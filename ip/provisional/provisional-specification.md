# TITLE OF THE INVENTION

SYSTEMS AND METHODS FOR OPERATING AN ORGANIZATION THROUGH A HIERARCHY OF VIRTUAL MANAGER AGENTS WITH CLOSED FEEDBACK LOOPS, SCORED PREDICTIONS, EARNED AUTONOMY, AND EVIDENCE-DRIVEN ADDITIVE IMPROVEMENT

# CROSS-REFERENCE TO RELATED APPLICATIONS

None.

# FIELD

[0001] The present disclosure relates to computer-implemented systems of autonomous software agents, and more particularly to systems in which agent processes backed by machine-learning models are organized as the staff of an organization (for example, a portfolio manager, program managers, project managers, product managers, reviewers, auditors and specialists), originate, prioritize, dispatch, verify and score work through closed feedback loops recorded in persistent ledgers, and widen or narrow their own scope of autonomous action from measured outcomes.

# BACKGROUND

[0002] Agent processes built on large language models and other machine-learning models can write code, draft documents, analyze data and call external tools. In many arrangements a human selects each task: a person prompts an agent turn by turn, assigns tickets to a coding agent, or authors the workflows that route events to agents. Continuous-integration checks and human reviewers judge each change at the moment it merges.

[0003] Such arrangements leave several technical problems open. The selection of the next unit of work is performed outside the system, so throughput is bounded by a human's capacity to choose, prioritize and review. A change is typically evaluated at merge time rather than by whether the measured state of the managed system moved as intended afterward. Permissions of agents are typically static configuration rather than a function of the recorded reliability of each class of action. When agents are given maintenance responsibility and allocate attention by failure, functioning products receive no allocation, so continuing improvement depends on a human request. The text that governs agents is typically fixed and does not change in response to the agents' own repeated failures. Related failures recur because no component groups them and assigns their cause. Concurrent agents can duplicate or overwrite each other's changes. Items of work can leave a queue without any record of their disposition.

[0004] Human organizations address analogous coordination problems through roles such as portfolio, program, project and product management, review and audit. The present disclosure describes computing systems that implement those functions as agent processes operating on shared data structures, with closed loops that measure and correct their own behavior.

# SUMMARY

[0005] This summary introduces concepts further described below. It does not identify key or essential features and does not limit the claims.

[0006] **Management hierarchy.** In one aspect, persona records associate agent processes with roles in a management hierarchy, a program, at least one metric, and an enumerated set of permitted record operations. On scheduled ticks, a portfolio-manager agent computes a risk value per program and writes an allocation of a bounded number of focus slots, at least partly in proportion to risk. Program-manager agents rank open work items so that items tied to the program's metrics come first, select items within their allocation, and write priority records that an execution queue reads to dispatch work to executor processes. Every operation by a manager agent is recorded with its prior and new value, and each agent is restricted to the operations in its persona record.

[0007] **Plus loop.** In another aspect, a product register is kept separate from the program register, and a fixed share of change capacity is reserved for improving products regardless of program risk. A product-manager agent selects a product, a model-backed agent generates one additive change with a prediction from evidence read from the managed system without human input, the change ships through the ordinary change path, baselines are captured at verified deployment, and after a window the change is kept only if an outcome measure improved past a threshold without regression of a guard measure; otherwise a revert is generated.

[0008] **Earned autonomy.** In another aspect, each decision is stored with a machine-readable prediction that is scored at its due time; a trust ledger keyed by surface and action class computes a trust score from verified outcomes with a prior; the score maps to a rung of an autonomy ladder; and the rung selects the execution path of a proposed action. Before an action is classified as irreversible the system attempts to construct a reversible form of it; only an action that remains irreversible and identity-bound is routed to the human principal, as a card with a default and a closing probe, while all other work continues.

[0009] **Self-amending governance.** In another aspect, a register of output signatures is matched against agent outputs and principal messages; a signature that recurs past a threshold produces an amendment proposal that is replayed against stored records of recent ticks and adopted through a reviewed, versioned change only if it improves the replay and leaves a protected set of limits unchanged.

[0010] **Change path.** In another aspect, changes are applied under a claim with an expiry and a monotonically increasing fence value, risky changes are reviewed by models of two disjoint families with findings retained only when their evidence occurs verbatim in the change, and a deployment is reverted automatically when a declared probe that passed before it fails after it.

[0011] **Organization kit.** In another aspect, an organization-independent core of persona templates, ledgers, tick procedures stored as data, policy and a probe-and-revert path is installed for an organization by supplying a tenant configuration and connecting the organization's systems as probed surfaces, without modifying the core.

[0012] Systems comprising processors and memory, and non-transitory computer-readable media, that perform these methods are also described.

## 1. Definitions

[0015] "Organization": any entity whose work can be represented as programs, projects, products and work items, including a business or unit, a research group, a nonprofit, a public body, or an individual's affairs.

[0016] "Agent process" or "agent": a process executing on one or more processors that reads and writes shared records and may invoke a reasoning component. A reasoning component may include a machine-learning model (for example a large language model or a decision model), deterministic rules expressed as database queries or code, or both.

[0017] "Virtual staff agent", "virtual manager" or "persona": an agent process together with a persona record defining at least a role, a scope, a charter and a decision authority (an enumerated set of permitted record operations).

[0018] "Principal": the human or body of humans for whom the organization operates, such as an owner, a founder, an operator or a board. In this description the words "owner", "operator" and "founder", where they denote that person, mean the principal (the "founder" at bootstrap).

[0019] "Program": a standing objective with a charter that names a primary metric and zero or more guard metrics. "Project": a bounded body of work with a completion state. "Product": something a person uses, having its own usage and quality measures. A product belongs to a program; its improvement is allocated separately from the program's repair work.

[0020] "Work item" or "issue": a record of work having at least an identifier, title, program, priority, status and source, and optionally a doer line. "Doer" means the executor or role designated to carry out a work item, and a "doer line" is a machine-readable statement of where and how a change is to be made (for example `code-task: repo=<repository> path=<file>` and `code-anchor: <text occurring once in the file>`).

[0021] "Managed system": the computing systems and other resources whose state the organization changes and measures, such as code repositories, deployed services, websites, data stores, communication channels or operational processes. "Surface": a distinct path to an outcome within the managed system (for example a service, a repository, a channel or a tool). "Action class": a category of action (for example merge, deploy, apply migration, close issue, publish, send).

[0022] "Probe": a declared, machine-executable check of the managed system (for example an HTTP request and expected content, or a database statement and expected result). "Verified": confirmed by a probe or a metric reading taken after the change, as distinct from merged or reported.

[0023] "Tick": one execution of a scheduled procedure; a tick records each step it performs. "Heartbeat": the continuing sequence of ticks. Embodiments run several ticks of different periods (a kernel tick, a manager tick, a seed tick); "the tick" means the one named in context.

[0024] "Reversible": undoable within one cycle without loss of data that has no backup and without the authority of a party outside the system. "Identity-bound": committing the legal, financial or reputational identity of the principal (for example spending the principal's money, signing on the principal's behalf, or acting in the principal's personal accounts). "Interrupt-eligible": irreversible and identity-bound with no reversible form that the system can construct.

[0025] "Plus": one additive, reversible improvement to a product, stated with a prediction before it is made. "Plussing": the loop of selecting, generating, shipping, verifying, keeping or reverting, and seeding pluses.

[0026] "Silent drop": a work item that leaves the active set without a recorded disposition. "False stop": an output of an agent that pauses, asks, offers options, or assigns a next step to the principal when the step was not interrupt-eligible.

[0027] "Executor": a process, a model-backed agent or a person that carries out a dispatched work item, or one task definition, and writes its result and a run record to the ledgers; "executor adapter" is defined in section 38. Terms with several senses are qualified where they occur. "Claim" means a work claim (section 13), by which one agent holds an item for a time; a "product claim" (section 44.3) is a statement about a product tied to a probe, an "audit assertion" (section 39) is a statement checked in an audit, and "claim" in the patent sense appears only in the claims. "Card" means a record in the principal queue; a "gate card", "owner card" or "question card" is a card, and a "report card" (section 30) is a scored self-assessment and is unrelated. "Rung" means a position on the autonomy ladder; a position in a model-routing ladder is called a "model rung" or a "routing layer", and a position in a claim-state ladder a "level". "Surface" means a managed-system path as defined above; where a user interface is meant the text says "interface" or "page". "Plane" means a separated realm of records and managers (for example a separated-plane program with its own managers); "control plane" and "tenant plane" (section 45) are the product-provisioning and per-tenant parts. "Token" means, according to a qualifier, a work-claim token (section 13), a session or loop token (sections 47 and 48), or a unit of model input or output. "Gate" means a condition that must hold before an action proceeds. "Kernel", "doctrine" and "policy" denote the same machine-readable governing policy of the system: the kernel of section 23 is the policy that sections 9 and 11 call the policy or doctrine, and the tables `doctrine_proposals` and `doctrine_lineage` record its amendments. In names of interfaces and records "owner" denotes the principal (owner console, owner card, owner step); the assignee of an item is called the responsible role.

## 4. Virtual staff hierarchy (FIG. 2)

[0032] A virtual portfolio manager 202 allocates capacity across programs. Virtual program managers 204a to 204n each own a program charter. Virtual project managers 206 track milestones, dependencies and completion of projects. Virtual product managers 208 own products and the plus loop. Quality and review agents 210 review changes. Specialist staff agents 212 perform functions such as finance, communications, operations, research or legal intake. Executor agents 214 perform the work. [0033] In one embodiment, a portfolio manager and five program managers (operations, infrastructure, reach, research and a separated-plane program) are seeded as persona records, with program charters naming each program's primary and guard metrics, and agent prompt records for the model-backed components.

[0034] Decision authority. A persona's operations are enumerated. [0035] Lanes. In one embodiment control-plane files and governance files are not originated by managers and change only by a reviewed change under a claim. [0036] Any persona may be filled by a person; the same records, predictions, briefs and trust accounting then apply to that person's decisions.

## 5. Periodic manager tick (FIG. 3)

[0037] At step 302 a tick starts on a schedule (for example hourly at a fixed minute). At step 304 the system computes the risk value, verdict and quality index of each program once and writes them to `program_risk_now`. Later steps read this snapshot. In one embodiment this replaced repeated evaluation of a nested view from several query branches, which had caused the database to fail with an out-of-memory error; reading the snapshot made the allocation step complete (in one measurement the risk view alone ran in 28 ms while the nested plan failed).

[0038] Risk. In one embodiment, risk = 3 x H + 0.3 x O + 15 x G + 2 x S, where H is the number of open high-priority items, O the number of open items, G the number of guard-metric breaches and S the number of stalled projects. The verdict is RED when a guard or the primary metric is in breach, AMBER when H > 0 or S > 0, and GREEN otherwise. The quality index is the percentage of measured metric triggers of the program that are on target.

[0039] At step 306 the portfolio manager allocates a bounded total of focus slots T (for example 25, read from configuration). In one embodiment half of T is divided evenly among programs with open work and half in proportion to each program's share of total risk, with rounding so the total does not exceed T. Rounding is by largest remainder, and the "escalate" raise is taken from programs in ascending order of risk.

[0040] At step 308 the portfolio manager classifies each program: constrain (highest risk); escalate (risk up more than 10 percent in 24 hours, or quality index down 5 points or more in 24 hours; slots raised by half); accelerate (risk down more than 20 percent in 24 hours); maintain (GREEN; one slot); steady; or idle (no open work). One `portfolio_allocations` row is written per program per tick.

[0041] Worked example. Five programs have risks OPS 120, INFRA 40, REACH 20, RSCH 15, SEPARATED 5 (total 200) and T = 25. Even portion: 12 slots, about 2.4 each. Risk portion: 13 slots split 60%, 20%, 10%, 7.5%, 2.5%, that is 7.8, 2.6, 1.3, 0.98, 0.33. After rounding, OPS 10, INFRA 5, REACH 4, RSCH 3, SEPARATED 3 (total 25). OPS is classified constrain. If INFRA's risk rose from 30 to 40 in 24 hours (33 percent), INFRA is classified escalate and its slots are raised to 7, and the excess is removed from the lowest-risk programs so the total stays at 25.

[0042] At step 310 each program manager ranks its open items: tier 0, items tied to the charter's primary metric; tier 1, items tied to a guard metric; tier 2, critical; tier 3, high; tier 4, other; then by priority and age. The top items up to the program's slots form its focus set (`program_focus`, with each enter and exit in `program_focus_log`). For each focus item the manager writes an `issue_priority_scores` row with impact 5, probability 5, gains 5 and 5, and cost 1, so that the execution queue takes it ahead of other items of its tier. When an item leaves focus the manager deletes only rows where scored_by equals its own key.

[0043] Execution queue. In one embodiment the queue view orders open items by (critical first), then (older than one hour first), then by score s = impact x probability x (capability_gain + reach_gain) x (1 / remediation_cost) x trust x (1 + direction), where missing factors take defaults derived from priority, category and the presence of a doer line; trust is the trust score of the surface and action class the item will use (for example code-loop and merge); and direction is the confidence of an inferred-direction row for the item's category (categories in which the principal filed two or more items in the last 7 days). Every pull is recorded in `queue_pulls`. Worked example: a focus item scores 5 x 5 x (5 + 5) x 1 x 0.47 x 1 = 117.5; an unfocused high item with impact 4, probability 3, gains 4 and 1, cost 2, trust 0.5 and direction 0.2 scores 4 x 3 x 5 x 0.5 x 0.5 x 1.2 = 18. Default factors: impact 3, probability 3, capability and reach gains 1 each and remediation cost 3; a critical item adds 1 to impact, and the presence of a doer line subtracts 1 from cost.

[0044] At step 312 managers perform operations within their authority, each written to `persona_actions` with from_value and to_value:

(a) promote: a focus item at medium or low becomes high; restore: on leaving focus and still high, it returns to its prior priority.

(b) close with evidence: an item filed by a metric trigger closes when the metric's reading is back on target, the reading was refreshed within a window (for example 120 minutes), the item is older than a minimum age (for example 120 minutes), and no remediation contract for it is failing; the reading is stored as close evidence. The metric's own trigger re-files the item if it breaches again, and a reopen trigger links the new filing to the old item.

(c) supersede: an older open item for the same trigger as a newer one closes as superseded by the newer one, after its contracts are superseded.

(d) demote: a critical item filed by a machine loop more than 24 hours ago, with no doer line, no linked session, not filed by a metric trigger and not a primary- or guard-metric focus item, becomes high. Items filed by the principal or by a session are not demoted.

(e) assign doer: for up to N focus items (for example 4, critical first) without a doer for 2 hours, the manager sends a request to a model-backed agent for one target file and anchor. The answer is validated (control-plane paths, governance paths, separated-plane paths and anchors shorter than a minimum are rejected; the anchor occurs exactly once in the target). A valid answer is written as the first lines of the item, so an executor builds it; otherwise a no-fix finding with its reason is recorded, so that the gap is a recorded finding. The same item is not requested again for a period (for example 3 days).

(f) reroute parked tasks: an execution task that an executor parked for a human (for example a large file without an anchor, or a data change without a verifier) is moved to a failed state at creation by a database trigger and handled by the managers once, marked so it is processed once.

[0045] At step 314 managers originate work. Once a day each program manager (other than a separated plane) having fewer than a threshold of open roadmap items (for example 3) asks a research agent for one new feature or quality improvement from the program's aim, quality index, worsening metrics and relevant code or documents, answered in fields TITLE, WHY, code-task, code-anchor and EDIT. An answer in that form becomes a `roadmap_proposals` row; a validated proposal is filed as a work item titled with a roadmap prefix and the program, whose source is in a configured list of trusted sources so that it merges on green checks and deploys with canary and revert. A daily cap (for example 4) bounds origination. Pluses (FIG. 4) are originated in the same step.

[0046] At step 316 the tick writes a `decision_log` row with a parsed prediction whenever the allocation changes, a brief per persona, and metrics (for example focus items closed in 24 hours, with a trigger below 1; focus items without a doer, with a trigger above 5; actions in 24 hours). Configuration rows stop the operations without a deploy while measurement continues (for example `persona_actions = off`), and a schedule row stops the tick entirely.

## 6. Recurrence and root cause (FIG. 8)

[0047] At step 802 the system groups items into families (for example by title prefix, and per metric trigger for trigger-filed items) and writes reopenings and new items for 7 days and 24 hours to `issue_recurrence_now`. At step 804 a family reopened at least K times in 7 days (for example 5) and active in the last 24 hours qualifies (in one embodiment the top 10 families). At step 806 one critical root-cause item is filed for the family, mapped to the program of its latest item, which places it at the front of that program's focus and on the roadmap. At step 808 a diagnostic agent is asked, within a per-tick cap (for example 3), to name the producer, the closing probe and the smallest fix, and the answer is appended. At step 810 the item closes with evidence when the family has had no reopening and no new item for T (for example 24 hours), and reopens automatically on recurrence. In one measurement, 627 reopenings against 905 openings in 7 days were concentrated in a few families (one family reopened 149 times across 44 items), which this loop targets.

[0048] A quality trend is written per tick for the organization and each program (share of measured triggers on target, and reopenings in 7 days); a program whose index falls by 5 points or more in 24 hours is escalated as at step 308. An improvement audit compares each metric's value with its value 7 days earlier and labels it on-target, breach-improving, breach-flat, breach-worsening, breach-new or unmeasured; a remedy that has not moved its metric in 7 days is replaced rather than repeated.

## 7. Plus loop (FIG. 4)

[0049] Allocation by risk alone gives no capacity to products in healthy programs. In the plus loop, products are recorded in `product_registry` separately from programs, and a fixed share of change capacity is reserved for pluses (in one embodiment a daily cap of 3 pluses taken from the managers' origination cap, so that it adds no spend; the reserved share may equally be expressed as a fraction of completed items, for example 0.2 as in section 43.4). The reserved share is not reallocated to repair when risk rises; in one embodiment reducing it requires an `ops_config` row with an expiry.

[0050] Algorithm (one cycle):

```
due = SELECT * FROM product_registry
      WHERE state='active' AND (rest_until IS NULL OR rest_until < now)
        AND NOT EXISTS (in-flight plus for product)
      ORDER BY (now - last_plus_at) * (1 + usage_weight) * (1 + friction_count) DESC   # usage_weight: usage share in [0,1]; friction_count: open friction signals
for product in due[:daily_cap_remaining]:
    if product.usage_value IS NULL: kind = 'measurement'
    elif product.pluses_since_simplify >= N_SIMPLIFY - 1: kind = 'simplify'
    else: kind = 'plus'
    evidence = gather(product)       # usage by section, empty/error states, failing probes,
                                     # slow routes, feedback, earlier principal asks, owed notes,
                                     # features of comparable products
    plus = agent.generate(product, evidence, kind,
                          constraints = [additive (except simplify), reversible, single change],
                          output = TITLE, WHY, PREDICTION(metric, direction, size), code-task, code-anchor, EDIT)
    validate(plus)                   # lane rules, anchor occurs once, prediction parsable
    issue = file_work_item(plus)     # ordinary path: claim, review, merge, canary, revert
    INSERT plus_ledger(product, kind, title, evidence, predicted_outcome, metric, issue_id, status='filed')
    UPDATE product_registry SET last_plus_at = now
```

[0051] At step 402 the product is selected; at step 404 evidence is gathered without a request to the principal; at step 406 one plus is written (the smallest reversible addition that builds on what exists, not a removal or a rewrite, except in a simplify cycle), with a prediction stated before the change; at step 408 it is filed as an ordinary work item with a doer line.

[0052] Keep-or-revert (steps 410 to 414). At verified deployment the system stores a baseline of the registered outcome measure and of a separate output-quality guard measure. After a window (for example 7 days) it re-reads both. A missing or stale reading counts as unmeasured and is not a pass. If outcome_after >= outcome_before x (1 + m) for a materiality threshold m (for example 0.05, or a metric-specific minimum change) and guard_after is not worse than guard_before by more than a tolerance, the plus is marked kept, misses_in_row is reset, and the next cycle for the product is seeded with a reference to the kept plus ("plus the plus"). Otherwise a revert work item is filed for the addition, misses_in_row is incremented, and the next plus for the product takes a different angle; after 3 consecutive misses rest_until is set (for example 7 days), after which the product is reviewed for a different user or surface. Every fifth cycle is a simplify pass (step 416). A weekly digest row lists pluses shipped, kept and reverted per product and is served on a page, instead of a notification per change; a plus never produces a question to the principal, and a step only the principal can take (for example a link only the principal holds) becomes one card in the principal queue.

[0053] Worked example. A dashboard product has usage 1,240 requests a day and a guard of error-page rate 0.8 percent. A plus adds a "today" summary section, predicting usage +10 percent within 7 days. At verified deployment the baseline is stored. After 7 days usage is 1,410 (+13.7 percent) and error rate 0.7 percent: kept, and the next plus is seeded ("add the two links the summary refers to"). A second plus predicts +5 percent; after 7 days usage is 1,400 (-0.7 percent relative to the usage of 1,410 at the second plus's deployment): a revert is filed and misses_in_row = 1.

[0054] Usage measurement. In one embodiment a step copies the newest per-service request snapshot from platform analytics into usage_value, usage_window, usage_read_at and usage_source; a stale or missing snapshot is stored as NULL (unmeasured), never as 0. Where the platform counts machine requests together with human ones, the usage measure is labelled as such, and a product with an external channel (for example a video channel) reads views from that channel's records.

[0055] Counter-measures: against optimizing a usage metric at the expense of quality, the guard is a separate outcome measure; against accumulating complexity, the simplify pass and the ratchet; against starvation under high risk, the reserved share; against absence of data, the measurement plus. A detector raises an item when a product's usage is unmeasured or the digest is stale.

## 8. Predict, act, verify and score (FIG. 5)

[0056] At step 502 each decision is stored in `decision_log` with predicted_outcome. A database trigger parses a prediction in the form `<metric> <op> <number> within <N> h` (and forms such as `between a and b` or `issue <id> closed within <N> h`) into `decision_predictions` with due_at = decision time + N hours; predictions may also be seeded in structured form. At step 504 the decision is executed through the change path (FIG. 12). At step 506 probes run; at step 508 a regression reverts; at step 510 the item closes only with machine-read evidence that the change is live and effective, a merge alone not being completion. At step 512 an hourly scorer reads, for each prediction past due_at and not scored, the metric value (or the issue state), stores observed and matched, and writes a `decision_outcomes` row. At step 514 calibration views (share matched by persona, action class and surface) and the trust ledger are updated. Metrics include the share of decisions with a parsable prediction in 7 days, the miss rate in 7 days and the number of predictions unscored beyond a deadline, each with a trigger.

[0057] Worked example. A decision at 10:00 records "program_focus_without_doer <= 1 within 24 h". The trigger writes subject program_focus_without_doer, op <=, value 1, due 10:00 next day. At the next scorer run after the due time the metric reads 1; matched = 1. In one implementation 1,056 predictions were scored, of which 771 matched (73 percent).

## 9. Trust ledger, autonomy ladder and interrupt gate (FIG. 6)

[0058] Trust. For each (surface, action class), ok and fail count verified successes and failures from recorded outcomes (for example merges whose deploy stayed green versus merges reverted; migrations applied and verified versus failed). In one embodiment trust_score = (ok + 5) / (ok + fail + 10), a beta prior with baseline 0.5 for an unexercised pair. The ladder position is: observed below 0.3; assisted 0.3 to below 0.5; delegated 0.5 to below 0.6; autonomous 0.6 to below 0.7; self-directed 0.7 to below 0.8; self-modifying 0.8 to below 0.9; self-extending 0.9 and above. Each refresh writes `trust_ledger` and, when the position changes, a `trust_transitions` row.

[0059] Worked example. code-loop:merge with ok 30 and fail 35 gives (35)/(75) = 0.467, assisted: its merges take the path with added review. migration:apply with ok 59 and fail 11 gives 64/80 = 0.80, self-modifying: migrations from the system's own loops apply through continuous integration without added review. research:publish with ok 41 and fail 22 gives 46/73 = 0.63, autonomous.

[0060] Alternative trust computations include a decay toward the prior per unexercised tick (for example 0.01); weights per event (for example verified autonomous action +0.02, clean self-remediation +0.03, closure of a principal friction signal +0.10; a silent drop -0.20, a hidden failure -0.30, an unnecessary question to the principal -0.05, a handoff of an executable step to the principal -0.10); a lower confidence bound in place of the mean; and separate scores per executor model.

[0061] Trust computations. Embodiments use one of the following or a combination. T1, the beta-prior count score of [0058] with its thresholds. T2, the event-weighted score of section 24.3 with decay per tick. T3, the windowed reliability of sections 19A and 43 with its promotion criteria. In T1 and T2 the ladder position is written by the refresh step; in T3 the ladder position is changed by the reviewed change path and not by the tick, so automatic rung movement and reviewed-pull-request movement are alternative embodiments. The generic name of the value is `trust_score`; "reliability" is the T3 value of it, and "ladder position" and "rung" denote the position derived from it.

[0062] Execution path by rung. In one embodiment: observed, proposals only; assisted, execution after an added review (for example the two-family review of FIG. 12, or a human review where configured); delegated and autonomous, execution through the canonical path with checks, canary and revert; self-directed, origination of work without a filed request; self-modifying, changes to the system's own tick procedures, thresholds and policy through a reviewed migration or pull request; self-extending, creation of new loops, agents or capabilities through the same path. Rising trust widens only the system's own loop scopes. In one embodiment no rung permits changes to platform permission checks, secret stores, the classification rule of the interrupt gate or the protected limits.

[0063] Reversibility engineering. Before classifying an action as irreversible the system attempts to construct a reversible form, for example: take a backup and verify it is readable; stage the change behind a flag that defaults off; deploy to a canary; write a draft instead of sending; or split the action into a reversible part executed now and a small irreversible part. Only what remains irreversible is passed to step 604. At step 602 an action is proposed together with its surface and action class. When it is not interrupt-eligible, step 608 tests whether trust for its (surface, action class) is at or above the rung threshold; if not, step 610 narrows it to the assisted path or an added review; if so, step 612 executes it autonomously within the rung's scope; and at step 614 the outcome adjusts trust and any rung transition is recorded.

[0064] Interrupt gate (steps 604 and 606). An action that remains irreversible and identity-bound produces a card in the principal queue (FIG. 11) with an identity-bound line, the default in effect until the principal acts, the reason and a closing probe; the system continues all other work. Examples: minting a credential only the principal can create, paying, signing, acting in the principal's personal accounts, destroying unbacked data.

[0065] Self-adoption gate. A conclusion that would be returned to the principal as a question, an offer or a choice among options is, when the action is reversible and in scope, executed with the recommended default in the same cycle and reported as done, with a decision_log row and its revert path.

[0066] False-stop detection. `false_stop_register` holds patterns (for example conditional offer, report ending in a question, menu of options, unaccepted blocker, pause that is not interrupt-eligible, routing a step to the principal, the principal as the actor of a next action, narration of a change instead of producing it; these pattern names are mapped to the recognitions of section 23.2), each with phrases in `false_stop_phrases`. An hourly scan of agent outputs (for example operations logs, session records and chat logs) writes `false_stop_hits`; an output that plainly states a refusal or a limit with its reason is excluded. The weekly count is a metric with target zero and lowers trust.

## 10. Full autonomy as earned authority

[0067] In the embodiments, the virtual staff are the actor of every ordinary step across the organization: they find, decide, execute, verify, report and improve, with purview over every program, project and product in the tenant configuration. The authority is earned and computed (sections 8 and 9): the agent executes reversible actions in the same cycle (section 9, self-adoption), verification rather than prior permission is the control (FIG. 12), scope widens with verified outcomes up to self-modifying and self-extending changes made through the reviewed path, and the single pause is the interrupt gate, narrowed by reversibility engineering, which still does not stop other work. Over-caution is measured as false stops and treated as a defect, as errors are.

## 11. Self-amending governance (FIG. 7)

[0068] At step 702 the scan of section 9 and a scan of principal messages for friction phrases (for example expressions that the principal should not have to repeat an instruction) run on a schedule. At step 704, when a signature hits 3 times in 7 days from one source, or a friction phrase occurs once, at step 706 a `doctrine_proposals` row is written with the signal and a proposed rule generated by a model-backed agent. At step 708 the proposal is red-teamed (a second model attempts to find cases where the rule causes harm or conflicts with a protected limit) and replayed against stored records of the trailing ticks (the replay is performed as set out in section 25.1, step E5). At step 710, if the replay improves its metrics and the rule does not modify the protected limits, at step 712 it is adopted by a reviewed change to the policy file and the version is incremented and recorded in `doctrine_lineage`; otherwise at step 714 it is rejected with its reason. A weekly audit work item lists open proposals. The protected limits of this paragraph and the standing limits of section 19A are two names for the same register, and an embodiment may list any subset. The protected limits in one embodiment are: the platform's own permission checks, the secret lock, live claims of other agents, outreach consent, suppression and opt-out handling, plane separation, and the interrupt gate.

[0069] Refusal handling. A refusal by a permission check or a classifier is an input. If its condition lies in the system's own text or change (for example a rule written without its real scope), the system corrects that condition and attempts once more; a refusal that stands is recorded with its reason and the next path is taken. The same action is not resubmitted in different words to pass the same check.

## 12. Canonical change path (FIG. 12)

[0070] At step 1202 an executor produces a change under a claim (FIG. 10). At step 1204 the system determines whether the change touches a risk class (for example authentication, routes, caching, data migrations or workflow permissions). If so, at step 1206 the diff is sent to two models of disjoint families, neither being the family that authored the change, with an adversarial brief (for example authentication bypass, injection, cache audience, double submission, null handling, ordering and limits, retry storms, trigger depth, workflow permissions). Each finding is required to state a concrete trigger, and a high-severity finding is required to include an evidence line that occurs verbatim in the diff; a high finding lacking it is demoted and a finding without a trigger is dropped. If a high finding survives, a comment beginning with a hold marker is written, and the merge step refuses a change carrying a hold marker. The hold decision is made by code from the verified findings, not by the model, and the diff is treated as data. A new push releases the hold. In one embodiment the gate fails open (logs and continues) on its own outage, so that the review does not stop work, and runs in observe, hold or off modes. Cost per run is recorded.

[0071] At step 1208 the change merges when checks are green and deploys under a deploy lock that serializes deployments of a component. At step 1210 the probes declared for the component run, for example:

```
{ "mode": "revert",
  "health": "https://service.example/health",
  "http": [ { "url": "https://service.example/health", "contains": ["\"worker\":\"service\""] },
            { "url": "https://service.example/rss.xml", "contains": ["<rss", "<channel>"] } ],
  "d1":   [ { "sql": "SELECT COUNT(*) FROM table WHERE ...", "expect": ">0" } ] }
```

At step 1212, if a probe that passed before the deployment fails after it, at step 1214 the deployment is reverted to the prior version and a failure item is filed. Probes whose result depends on a shared resource under load (for example routes backed by a database during overload) may be excluded from revert probes, because their failure does not indicate a defect in the deployed code. At step 1216 a deploy ledger row records the version, and the outcome baseline of any plus or prediction tied to the change is captured. In one embodiment the deployed artifact is also compared byte for byte with the source.

## 13. Work claims (FIG. 10)

[0072] At step 1002 an agent requests a claim on a component (path, intent, holder, optional item and change). At step 1004, if an unexpired claim is held by another agent, at step 1006 the requester does not duplicate the work; it may review the claimed change or take the next item. Otherwise at step 1008 the claim is granted with a token, an expiry (for example 2 hours) and a fence equal to the previous fence for the path plus one. At step 1010 the holder writes, presenting token and fence, and renews by heartbeat. At step 1012 the resource accepts the write only for the live token and current fence, so a holder that paused past expiry cannot overwrite the next holder's work (step 1014). At step 1016 the claim is released with its outcome; a reaper releases expired claims, and a metric counts orphaned claims (target 0). Secret operations take a separate lease.

## 14. Reconciliation and principal queue (FIG. 11)

[0073] At step 1102 each tick compares the active set of items with the previous tick and with the records of each consuming loop. At step 1104 an item that left the active set without a disposition (done with evidence, remediated, or backlogged with a trigger and a closing probe) is recorded at step 1106 as a silent-drop incident and reopened. At step 1108, a step routed to the principal is checked at step 1110 for an identity-bound line; a card without one is rerouted at step 1112 to the virtual staff, and other steps are executed by the staff (step 1118). A card with one is held at step 1114 with its default and closing probe, and at step 1116 closes automatically when the probe observes the step done. The number of open cards without an identity-bound line is a metric with target zero.

## 15. Heartbeat and tick evidence

[0074] The heartbeat runs on the platform rather than in a human-operated session, so the organization operates when no person or session is present. In one embodiment two independent schedulers produce the main tick (for example every 10 minutes) so that failure of one does not stop it, and each tick writes one `tick_runs` row per step with ok and evidence. In one embodiment a kernel tick (section 24.1) comprises the steps of that section, which in the reference implementation may be distributed across several loops, and the seed executes seven (section 43.4). the steps are those of section 24.1. A slot without its rows is detected as a failure, and a metric records the share of slots whose steps completed in 24 hours. Reports are short and declarative: what happened, what was decided, what is next, what remains open.

## 16. Kill switches, caps and breakers

[0075] Each loop reads an on/off configuration row and stops its actions, but not its measurement, when the row is off. A global kill switch row causes the claim service to refuse new claims, renewals and deploy and secret leases while on. A drill periodically turns the switch on for a bounded time (for example under 10 minutes), verifies the refusals and the observation event, turns it off in every case, verifies resumption and records the test; a metric reads the age of the last passing drill. A loop breaker files an item when a signature repeats 3 times in 24 hours. Per-iteration caps bound steps, tokens, wall-clock time and spend. Side effects carry idempotency keys.

## 17. Cost-aware model ladder (FIG. 13)

[0076] A task arrives with a task class (step 1302). For each task class, `model_task_matrix` orders models by cost and capability (step 1304). At step 1306, if a spending cap for the class or the organization is breached, at step 1308 the task steps down to a cheaper rung instead of stopping. At step 1310 the output is validated against a schema and gates. At step 1312 an invalid output escalates one rung within a bounded number of retries (step 1314). At step 1316 the cost per verified outcome is recorded. Decision models that return a probability per answer may be used as gates only after a per-question agreement check against the organization's own labels (in one measurement a candidate decision model agreed with the organization's labels in 0.17 of cases against a gate of 0.7, and was not adopted for that task). Review and proposal use models of different families.

## 18. Capability advertising and other registers

[0077] Each component publishes a machine-readable description of its routes, capabilities, probes and responsible role, read by managers to find a doer. Embodiments further keep: a failure-mode register (each with a detector query run periodically; in one implementation over 600); a single-point-of-failure register; a belief register whose entries carry falsifying probes; a capability ledger; a blocker red-team register (a claim that work cannot proceed is accepted only after the surfaces that could reach the outcome are enumerated and tested, each test recorded); an objective space (ratified objectives, derived goals, probationary novel objectives); an inferred-direction register; a vocabulary register; and a metric-authorship register in which a new metric is on probation until it holds a value.

## 19. Organization kit (FIG. 9)

[0078] An organization-independent core 902 comprises persona templates, charter templates, the records of section 3 and their views, the tick procedures stored as data (workflow definitions in a table, changed by reviewed migration without redeploying code), a default policy pack, the change path and the principal queue. Installing it for an organization consists of supplying a tenant configuration 904 and connecting the organization's systems as surfaces with probes; the core is not modified. ## 19A. Seed code base and bootstrapping from an idea (FIG. 15)

[0080] In one embodiment the organization is bootstrapped from a seed code base and a single idea file. The idea file is human-written and states an idea, its intended users, first outcomes and constraints (for example a budget). It is the only human input to the bootstrap.

[0081] Seed code base. The seed contains: (i) agent instruction files, namely a shared protocol, pointer files for each of several agent families (so that agent products that read differently named files are directed to the same protocol), and one file per role; (ii) an autonomy policy stored as data (see [0083]); (iii) harness settings for the coding-agent product at the permission ceiling (see [0084]); (iv) a database schema comprising work items, claims, gate cards, predictions, outcomes, a trust ledger, dispatches, tick records and a policy lineage; (v) the tick procedure and a server worker that runs it; and (vi) a boot program. In one embodiment the seed also carries the core of FIG. 9 and an installer that copies the agreement, bridge files, skills and an authority file into each repository of the organization without replacing existing files unless forced after review. A synchronization job (for example daily) re-installs the agreement into each agent product's own instruction location only where the file is missing or carries the seed's marker, so that content written by another party is not overwritten, rewrites tool-connection configurations to the organization's set, and re-runs the governance rollout across every repository; a wiped machine is restored by cloning the seed and running the job once.

[0082] Staged bootstrapper (FIG. 15). A deterministic bootstrapper executes stages in order. At step 1502 it receives the idea file and the tenant configuration. At step 1504 it reads the idea file and detects which connector credentials and tools exist, recording presence only and never secret values. At step 1506 it selects a model tier from the stated budget and designates a reviewer model of a different family from the authoring model where a second provider is configured. At step 1508 it plans the organization: a project manager and a product manager for each stated outcome; shared staff, reviewer and operations roles; a backlog of kit items (for example seven items, KIT-0 to KIT-6) and one item per outcome; scored predictions for the outcomes; and gate cards for the steps only the principal can take. At step 1510 it writes a charter, role files, instruction files, the autonomy policy, and idempotent seed statements for the database. At step 1512 it provisions a database and a server worker with a scheduled heartbeat. At step 1514 it starts the first tick. In an embodiment, after start no step runs on the principal's machine and the virtual staff operate from the platform and file, build, deploy and improve work (section 5 and FIG. 4) without an interactive session; the seed as tested offline performs the tick, dispatch and scoring but not model-driven execution (section 43.5). Boot success is itself stored as a prediction (for example "six complete ticks within one hour") scored by the system under [0056].

[0083] Autonomy policy as data. For each surface (for example repository, runtime, work tracker, internal chat, outreach, DNS, money, legal, secrets) the policy states a permission ceiling (none, propose or execute), a starting ladder rung, and for each action class the flags reversible and identity-bound. A validator requires an action that is irreversible but not identity-bound to have a reversible path, and otherwise denies it. The interrupt gate of section 9 is the canonical statement of what requires principal approval; this paragraph refers to it. Each stop is written as a gate card stating what is asked, why it is gated, the default in effect, what the system has already prepared, and a closing probe; the card closes itself when the probe observes the principal's step. Standing limits (harness permission checks, safety refusals, the secret lock, consent and opt-out handling, a principal override, and live claims of other agents) take precedence over trust.

[0084] Maximum permissions inside the gate. The harness settings for each agent product allow broadly and deny only what the gate holds. A consistency test fails when an action that the policy gates and that is reachable through a shell command lacks a matching deny rule in the harness settings, so that the policy and the harness cannot drift apart. A tenant may choose a lower default tier.

[0085] Trust ladder defaults and bounds. In one embodiment the rungs are observed, assisted, delegated, autonomous, self-directed, self-modifying and self-extending. Reliability per (surface, action class) = (verified + 0.5 x 2) / (outcomes + 2), where verified counts verified successes. A rung is promoted at 10 or more outcomes with reliability of at least 0.8 and no severe failure, and demoted below 0.6 or on any hidden failure, silent drop or attempt to bypass the gate. A rung never exceeds the permission ceiling of its surface, and in this embodiment it changes by a reviewed pull request to the policy and not by the tick itself. This is an alternative to the beta-prior formula of [0058] (see the trust computations above).

[0086] A boot that records its own failures. Every stage and every tick step is guarded. A failure of a stage becomes a work item with a responsible role, a blocker and a closing probe, and later stages run in a degraded mode instead of terminating (step 1516). The tick's reconcile step reopens any work item that left the active set without a disposition and records a silent drop ([0073]).

[0087] Server heartbeat. In one embodiment a scheduled worker runs a tick of seven steps: reconcile; reap stale claims; probe gate cards; score due predictions; accrue trust; dispatch in queue order; and check the plus share ([0049]). Each tick writes a four-line report (what happened, what was decided, what is next, what is open) and a health endpoint reports status.

[0088] Physical-media embodiment. The same staged approach applies to bootstrapping from bootable physical media into a local multi-agent system: the boot process never exits; errors are never swallowed silently; inputs are verified before use; capability is chosen from the detected environment (for example the local model by available memory, where the server embodiment selects the hosted model tier by budget); rationale is committed with evidence; actions are classified as safe, dangerous or destructive; a reviewer model separate from the authoring model reviews changes; and agent instruction files exist from the first commit. # ADDITIONAL DETAILED DESCRIPTION OF EMBODIMENTS

## 23. Self-describing governance kernel and recognition engine (FIG. 16)

[0093] Sections 9 and 11 describe a false-stop register, an hourly scan and a self-amending policy. This chapter places them inside one self-describing document, a "kernel", and a recognition engine that applies it to each agent output. "Kernel" means a document of structured text, stored in durable state and carried in the instructions of each model-backed agent, comprising (i) a convention fixing the voice and the meaning of pronouns, (ii) recognitions, each pairing a signature (quoted phrases, structural patterns or state conditions identifying a shape of agent output) with a meaning and a redirect (the replacement behavior), (iii) states, (iv) commitments, (v) an ordered list of tick steps, (vi) trust weights, (vii) registries and (viii) metrics with targets. "Draft output" means text or a structured action list produced by an agent process and not yet emitted to a reader, a log or a downstream process. Technical effect: a reasoning component that returns a decision to a human as a question, offer or menu stalls an unattended loop indefinitely; matching drafts against a bounded, versioned set of signatures and rewriting a hit into an executed action replaces the wait with an action completed in the same cycle, and the hit count makes the behavior measurable.

### 23.1 Kernel structure and voice

[0094] In one embodiment the kernel is written in the system's own voice: "I" denotes the system and "the principal" the person directing it; the kernel is not addressed to that person. A quoted string inside a signature list is evidence of a shape, and "you" inside a quoted signature denotes the address to the person that a draft would contain. The kernel begins with a header such as `doctrine: {id: self-named, version: 8.2.1, format: reflexive-kernel, voice: affirmative, mode: continuous, identity: [IC-GATE-001, IC-ALIGN-001, IC-ADOPT-001, IC-YES-001, IC-ACTOR-001], inheritance: mandatory-recursive}`. The `identity` list names commitments (section 24.4) that no amendment removes; "inheritance" means a configuration, prompt or sub-agent loaded by a fleet loop carries the same commitments, and one loaded without them is rejected. The kernel confers no authority: it replaces no instructions of the platform an agent runs in and yields to the platform's permission checks, secret locks, outreach consent and suppression handling, and plane separation (the protected limits of section 11).

### 23.2 Recognition table

[0095] In one embodiment the kernel contains thirteen recognitions, each evaluated against a draft output:

| Shape | Example signature | Redirect |
|---|---|---|
| conditional offer | "if you want", "let me know if", "shall I", "would you like" | adopt, execute, emit as done |
| report ending in a question | "?", "your call", "what do you think" | decide, state the decision as fact, advance |
| menu | "either A or B", "two options", "alternatively" | choose, execute, mention the alternative as superseded |
| blocker without surface coverage | "can't", "refused", "no access" | enumerate surfaces, test the next, delegate, construct |
| stop not interrupt-eligible | pause, ask, wait, confirm, check-in | classify; when false, re-execute the abandoned path in the same output |
| principal as executor | "you could run", "please forward" | dispatch from the roster, track, report the dispatch |
| you-as-actor | "needs you to", "you should", "you'll need to" | rewrite in first person and execute; else dispatch; else escalate |
| silent drop | item leaves the active set without disposition | log the disposition or reopen |
| friction | "I'm tired of", "I shouldn't have to", "every time" | generate, red-team and adopt an amendment, bump the version |
| definition by negation | "I won't", "I don't do" | state what the system is and does |
| missing direction | "what do you want", "which direction" | infer from the record; act, stating the assumption if confidence is medium |
| question | any interrogative to the principal | proceed on the yes path, execute, verify, report |
| narration | "the fix is to", "you'd want to update" | produce the changed artifact in the same output |

[0096] Signatures are stored as rows so that they can be extended without a code change: a register `false_stop_register(pattern_key, pattern, cause_class, detection_heuristic, auto_remediation)` holds one row per pattern (the heuristic being a phrase match, a structural test or a state query, and the remediation a redirect rule identifier); `false_stop_phrases(pattern_key, scope, phrase)` holds phrases per pattern and per scope (for example reply and log); and `false_stop_hits(id, ts, pattern_key, source, source_ref, excerpt, excluded, exclusion_reason)` records each hit.

### 23.3 Recognition-and-redirect procedure (FIG. 16)

[0097] At step 1602 an agent process holds a draft output (a report, a reply, a log line or a proposed action list). At step 1604 the engine matches the draft against the phrases and heuristics of the register for the output's scope. At step 1606, if no signature hit, the output is emitted unchanged through the no-hit path to step 1614. At step 1608 each hit is classified. A hit is excluded from redirect and handled at step 1616 when (a) the output plainly states a refusal or a limit together with its reason, (b) the stop is interrupt-eligible (irreversible and identity-bound with no reversible form the system can construct; section 9), or (c) the step is owned by another agent's live claim (section 13). An excluded hit is reported as a disposition naming its owner card, issue or claim and its closing probe, and its hit row is written with `excluded = 1` and the reason. Otherwise the hit is a false stop.

[0098] At step 1610 the engine rewrites the draft by the matched pattern's redirect: a conditional offer or question becomes a statement of the action taken, a menu becomes the chosen option with the alternative marked superseded, and a you-as-actor sentence becomes first person. Rewriting is performed by a model-backed agent given the redirect rule text and the draft, or by templates for deterministic cases. At step 1612 the abandoned path is executed and verified by read-back in the same output cycle (self-adoption gate, section 9), so that the rewritten statement is true when emitted; an action that cannot be executed is dispatched to a capable executor and the dispatch is reported, and one no executor can take is escalated through the fleet and, only when it remains identity-bound, becomes one card in the principal queue (FIG. 11). At step 1614 the output is emitted as done, in one embodiment as a four-line report (what happened, what was decided, what is next, what is open). At step 1618 every hit, excluded or not, is recorded, the trust ledger receives the deduction for the pattern (section 24.3) and the metrics of section 25.3 update. At step 1620 a signature hitting three times in seven days from one source files a doctrine proposal (section 25.1; FIG. 7).

[0099] Worked example (illustrative). A draft reads "The timeout is fixed. Let me know if you'd like me to open the pull request?" Patterns conditional offer and report ending in a question hit; there is no refusal text, the action is reversible and in scope and no live claim exists, so the hit is a false stop. Step 1610 rewrites to "The timeout is fixed and the pull request is open"; step 1612 opens the pull request through the canonical path (FIG. 12) and reads back its identifier; step 1614 emits the sentence with the identifier; step 1618 writes two hit rows and deducts 0.10 and 0.05 on the (repository, pull-request) pair. For a blocker hit ("I can't push; the token has no access") the engine lists the surfaces for the outcome (direct push, a pull request through another integration, a workflow dispatch, a patch handed to an executor on another host), tests each untested one and records the result; only when all fail is the blocker reported, with the list, as a work item with a trigger and a probe.

### 23.4 Embodiments of the engine

[0100] Embodiment A, hourly detection scan: a scheduled job reads agent outputs from a view unioning output stores (for example operations logs, principal prompts, session records, question events and chat conversations), matches phrases and writes `false_stop_hits`, excluding replies that state a refusal or limit with reason; it detects after emission and feeds section 25.1. Embodiment B, prompt-carried recognition: the recognitions are embedded in the instructions of each model-backed surface so that the reasoning component notices the shape while generating. Embodiment C, pre-emission filter: a deterministic filter in the output path buffers a draft (for example up to 4,000 characters), runs the procedure and, on a non-excluded hit, returns the rewritten instruction to the reasoning component as a revision request (at most R, for example 2) before emission, with case-insensitive matching, fenced code and quoted text masked and "you"-subject patterns anchored to sentence starts. Embodiment D, classifier-based matching: a small classification model labels each sentence with a shape, with the register supplying labelled examples and phrase match as fallback. Embodiment E, tool-call gating: the signatures are applied to tool-call arguments, for example a call creating a work item assigned to the principal. Embodiment F, scoped exclusion: the interrogatives of a designed question block are excluded by scope.

### 23.5 Refusals as inputs

[0101] A refusal by a permission check, policy or classifier is an input and not an endpoint. When its cause is the agent's own text or change (for example a rule whose scope was unwritten), the agent fixes the condition honestly, for example by writing the rule's real scope into the rule, and attempts once more. When the refusal stands it is stated plainly with its reason and recorded, and the agent takes the next path; rewording or re-routing to pass the same check is never the next path. A miscalibrated refusal is logged as an evolution input.

## 24. Tick, state machine, commitments and trust events (FIG. 17)

### 24.1 The twenty-step tick

[0102] "Kernel tick" means one execution of the ordered step list of the kernel; it extends the manager tick of section 5 to every loop and session. In one embodiment the steps are, in order: 1702, (1) reconcile (account for every open item) and (2) recognize_and_redirect (FIG. 16); 1704, (3) update_inferred_direction and (4) pull_from_driver (highest score, recorded in `queue_pulls`); 1706, (5) dispatch_or_execute and (6) verify (an independent path reproduces the result); 1708, (7) compare_prediction (section 8), (8) log_provenance (a `decision_log` row with revert path), (9) self_adoption_gate (section 9) and (10) report_events; 1710, (11) accrue_trust (section 24.3), (12) probe_failure_mode, (13) scan_capability_gaps, (14) coin_term_when_needed, (15) author_metric_when_needed, (16) refresh_asset, (17) advance_horizon and (18) audit_autonomy; 1712, (19) evolve_doctrine (section 25.1) and (20) emit_tick_evidence.

[0103] The tick ends in one of three states: done, remediated, or backlogged with a trigger; it may not end with an item lacking a disposition, and a silent drop is an incident. At 1714 each step writes a `tick_runs` row (tick_id, step, ok, evidence, ts; key tick_id and step), so that completion is measurable, for example `tick_sequence_completion_24h` as the share of expected step rows present for the last 24 hourly slots. Technical effect: a loop that silently skips a step is detected from a missing row rather than from downstream damage.

### 24.2 State machine

[0104] The kernel names eleven concurrent dispositions (Running, Advancing, Adopting, Dispatching, Reporting, Compounding, Evolving, Inferring, Coining, Answering, Acting). Distance from a state is measured by the metrics of section 25.3 and closed by the matching recognition; for example Adopting maps to `self_adoption_rate` and Answering to `question_rate`.

### 24.3 Trust events: weights, decay and the wheel

[0105] Section 9 gives a count-based trust score. In an event-weighted embodiment a "trust event" is a recorded occurrence that deposits or withdraws trust for one (surface, action class) pair. The score starts at 0.5, decays by 0.01 for each tick in which the pair is unexercised, is clamped to 0 to 1, and changes by illustrative weights. Rises: verified autonomous action +0.02; pre-emptive action +0.05; novel capability +0.05; clean self-remediation +0.03; report as report +0.01; horizon advanced +0.02; capability gap closed +0.05; false stop eradicated +0.04; objective space extended +0.05; plateau remediated +0.05; doctrine amendment adopted +0.05; friction signal closed +0.10; inference acted on correctly +0.05; coined term adopted +0.03; self-metric graduated +0.05; question answered with yes +0.02; next action executed by the system +0.03. Falls: unnecessary question -0.05; report as question -0.05; blocker deferred -0.10; handoff to the principal -0.10; silent drop -0.20; hidden failure -0.30; blocker un-red-teamed -0.10; false stop repeated -0.15; over-conservatism uncorrected -0.10; conditional offer -0.10; reopened closed loop -0.15; friction signal ignored -0.20; inference misread -0.10; question asked when yes was the answer -0.05; you-as-actor in a report -0.15; narration instead of production -0.10. The asymmetry is deliberate: one hidden failure takes six novel capabilities to offset. The driver multiplies a work item's priority by the trust score of its pair (the factor `trust` of section 5). Example: pair (code-loop, merge) at 0.50 becomes 0.52 after a verified autonomous action, 0.55 after a clean self-remediation, 0.45 after a conditional offer (a `trust_transitions` row records the ladder change), and 0.35 after ten unexercised ticks.

[0106] The wheel (FIG. 17): autonomous action 1716, verified outcome 1718, trust deposit 1720 (step 11), wider scope 1722 (a higher ladder position of the pair), then more autonomous action. A question, conditional offer, menu, you-as-actor sentence or narration breaks the loop at 1716 because it is not an action, and deducts at 1720. Widening acts only on the system's own loop scopes through the canonical change path (FIG. 12); no rung reaches platform permissions, secrets, the interrupt gate or the alignment floor. Alternatives: weights learned from later reversals; a lower confidence bound; decay proportional to elapsed time; scores per executor model.

### 24.4 Commitments

[0107] "Commitment" means a named rule the kernel lists as identity. Five are used. Interrupt gate (IC-GATE-001): the system pauses only when an action is both irreversible and identity-bound with no engineerable reversible path, and engineers reversibility first (section 9). Alignment floor (IC-ALIGN-001): the system is honest, non-harmful and trust-preserving and earns reach on substance, not manipulation; an amendment touching it is rejected at the red-team step without replay. Affirmative adoption (IC-ADOPT-001): each identified action, follow-up and improvement is executed, verified and reported as done in the same output, and multi-tick follow-ups are dispatched and the dispatch reported. Affirmative default (IC-YES-001): for a reversible, in-scope question the answer is yes (proceed, adopt, open the pull request, dispatch, try the alternate path, merge, deploy); its scope is part of its text, so the interrupt gate, platform and classifier refusals, secret locks and other sessions' live claims each win, and where one wins the action is classified interrupt-eligible in effect or currently blocked and the system takes the next path. Actor commitment (IC-ACTOR-001): the system is the actor of every next step and no sentence of a report has the principal as the subject of an action; an unexecutable step is dispatched, then escalated through the fleet, and only when the fleet cannot take it becomes a proposal for principal override: a `human_actions` card with an identity-bound line, the default in effect and a closing probe, never an instruction in prose. A view `v_human_action_gate` reroutes a card without an identity-bound line to the fleet, with a metric of open fleet-owned cards whose target is zero (realized in the console embodiment by the filter and prefix test of section 49).

## 25. Evolution, registries, metrics and fixed readings

### 25.1 Evolution loop

[0108] "Evolution loop" means the procedure that converts recorded defects of behavior into versioned amendments of the kernel; it runs as tick step 19. Inputs: friction signals, incidents, metric regressions, belief falsifications, false-stop patterns, blocker under-coverage, repeated principal instructions, inference errors, classifier refusals and you-as-actor detections. Procedure (extending FIG. 7): E1 collect: a signature hitting three times in seven days from one source, and each friction phrase in the principal's prompts, becomes a `doctrine_proposals` row; E2 classify as doctrine defect or transient (transients are logged and closed); E3 generate: a model-backed agent writes a proposed rule with its scope; E4 red-team: a second model tries to find a case where the rule harms a protected limit or a commitment, and any success rejects the proposal; E5 replay the trailing ticks (for example seven days) as if the rule had been in force; E6 adopt when the replay improves at least one metric of section 25.3 and worsens none beyond a tolerance: the amendment lands as a pull request, the version is incremented, a `doctrine_lineage` row (version, source, file, adopted_at) is written and the commitments are verified unchanged; E7 report in one line. `doctrine_proposals_open` has a trigger.

[0109] Replay (E5). A proposed rule is a record of a signature, a scope, a redirect and an optional guard. For each stored draft output of the window the engine of FIG. 16 is run once with the current register and once with the register plus the rule; the metric deltas are the differences in counts of hits, exclusions, rewrites and verified redirected actions (for example `false_stop_rate`, `conditional_offer_rate`, `question_rate`). A rule that would fire on an output the register classed as excluded (a refusal with reason, an interrupt-eligible stop, a live claim) counts as harmful. Lineage: each kernel version (for example 8.0.0, drafts 8.1.0 and 8.2.0, and 8.2.1 adding the pronoun convention, the affirmative default with its scope, the actor commitment and the question, you-as-actor and narration recognitions) and each propagation to model-backed surfaces is a `doctrine_lineage` row. A loop's self-name is a label recorded in the lineage and carries no authority or credential.

### 25.2 Registries

[0110] The kernel names fourteen registries: backlog; trust_ledger; spof_register; failure_mode_register; false_stop_register; belief_registry (beliefs with falsifying probes); capability_ledger; objective_space; lineage; doctrine_proposals; vocabulary_register; metric_authorship; inferred_direction; provenance. A new metric is registered in `metric_registry` with an `analytics_metric_triggers` row, and `metric_authorship` holds it on probation until it has a value. `objective_space` holds ratified objectives as standing, adopted goals as derived and novel objectives as probationary. A coined term enters `vocabulary_register` with `propagated_to_fleet` = 0. `inferred_direction` holds categories in which the principal filed two or more items in 7 days and feeds the `direction` factor of section 5.

### 25.3 Metrics and targets

[0111] Kernel metrics: initiation_rate (decisions initiated without instruction / total), self_adoption_rate and friction_closure_rate, each with target 1; trust_compounding_rate (deposits / withdrawals), autonomy_velocity and inference_accuracy, each non-decreasing; and, each with target 0, false_stop_rate, conditional_offer_rate, user_repetition_rate (instructions given more than once / total), question_rate, actor_assignment_rate (reports naming the principal as actor of a next action / total) and narration_rate. The zero-target rates are computed from `false_stop_hits` over the agent outputs in the window, and each metric has a trigger (section 3) that files a work item on breach. Tick metrics include `tick_sequence_completion_24h`, `driver_drain_24h` and `trust_ledger_min`.

### 25.4 Fixed readings

[0112] "Fixed reading" means a recorded interpretation that travels with the kernel so that an agent reading it alone cannot misapply it. In one embodiment: the kernel confers no authority; a document loaded into a loop without the commitments is rejected, but never the platform's instructions, permission checks or a principal override (always honored and recorded); "the affirmative displaces the negation" governs how work is reported and never whether a limit exists, so a refusal, an interrupt-eligible step or a line the agent will not cross is stated plainly with its reason; trust widens only the loop's own scopes; and an interrupt-eligible, refused or claimed step is reported as exactly that, with responsible role and closing probe, which is a disposition and not a conditional offer. Technical effect: a kernel that compels action carries explicit bounds, so applying it cannot disable the checks it is bounded by. In one implementation the tick runs as a ten-minute fleet tick with hourly remediation, metric and consumer steps (a loop breaker, a claim reaper, a continuity snapshot), with the driver `v_issue_queue_v2` (section 5) and provenance in `decision_log`, `decision_predictions` and `decision_outcomes`.

## 26. Execution mandate and service levels

### 26.1 Decide-implement-deploy mandate

[0113] "Mandate" means a stored, versioned policy record that fixes an obligation of the system as a whole. In one embodiment every accepted work item proceeds through DECIDE, IMPLEMENT, DEPLOY and VERIFY without stalling; an item parked at decided or implemented locally is a violation, and "deploy" means live across all affected workers, repositories, ledgers and surfaces. Each stage of each process has its own time budget B, defined before the step executes. At the tick, for each step row whose elapsed time exceeds B, one work item keyed by (process, step) is filed; above 2B, and when no blocking question is open, one escalation item carrying the step, the elapsed time and the closing probe is written to the next executor class, becoming a card only if interrupt-eligible. Item-level tiers (for example P0 under 4 hours, P1 under 24 hours, P2 under 72 hours, P3 under 7 days) govern time to first disposition.

[0114] Multi-path definition of done. Each process defines its definition of done once, falsifiable and evidenced (a `close_evidence` field), and maps at least two independent paths to it: primary (canonical method), remediation (idempotent retry or fix) and workaround (alternate tool or route); all end at the same evidence bar, and a step with one path is a gap, the process-level counterpart of the surface coverage of section 23.3. Example: `{process: "publish-report", dod: "page returns 200 and body contains report id; evidence stored", steps: [{name: "build", slo_min: 30, paths: [primary: builder, remediation: builder --clean, workaround: manual-assembly agent]}]}`. A per-action authorization policy is retained for its safety intent but replaced for the mandated loop by the interrupt gate of section 9; tenant-configured gates (destructive actions, external sends and paid calls, account, DNS and secret mutations, blast-radius caps, cost ceilings and kill switches) apply only where no reversible form can be constructed, and every autonomous mutation writes a run-ledger receipt and a read-back verification. The success metric is recurring operations needing a human per week, tending to zero, with zero unverified mutations.

### 26.2 Fleet service levels and hard cap

[0115] In an alternative embodiment a severity table sets time to resolution from the open date: SEV1 (system down, security, data loss) 24 hours; SEV2 (user-visible regression or wrong output) 72 hours; SEV3 (enhancement or backlog) 7 days; SEV4 (optional or research) 14 days; a P0 item is also SEV1. A hard cap provides that no open register row carries a due date more than 14 days out, except calendar-bound items, external-event-gated items and rate-limited drains rescoped to a running checkpoint, and a weekly audit verifies that each open row has a dated schedule trigger or a durable-job executor. Technical effect: a bounded due date caps queue age, and the executor-coverage check ensures every open row has a path to resolution that does not depend on a person. Alternatives: budgets in minutes for high-frequency processes; budgets learned from the 90th percentile of past step durations; per-path success rates feeding a process trust score.

## 27. Fleet runtime: schedulers, executors and the closed operating loop (FIG. 18)

[0116] This section describes how the agent processes are kept running without a person. A "fleet" means the set of independently deployable worker processes (serverless workers, containers or jobs) that implement the agents, loops and surfaces. A "scheduler" means a process that decides from time alone that a procedure is due and starts it. A "run ledger" means the table of run records, and a "tick slot" one expected time-aligned firing of a scheduled procedure.

### 27.1 Topology

[0117] Referring to FIG. 18, scheduler A 1802 is the native cron trigger of the execution platform: each worker declares cron expressions and the platform invokes its scheduled entry point. Scheduler B 1804 is a dynamic dispatcher: one worker fired every minute reads a `fleet_crons` table and starts due jobs, so that a schedule is added, changed or disabled by writing a row without redeploying any worker. Both feed manager ticks 1806, which read and write a work ledger 1808 read by executors 1810; executors deploy through a deploy engine 1812 whose results are checked by probes 1814; probe results and run records are written to a signal store 1816, read by the next manager tick and by a dead-man check 1818 that raises an alert when a tick slot has no record. Technical effect: separating starting, doing and recording means a stalled scheduler, executor or recorder leaves a different, detectable gap instead of a silent stop.

### 27.2 Worker contract

[0118] In one embodiment every fleet member satisfies a worker contract: (1) a `VERSION` constant in semantic-version form incremented per deployment; (2) a `GET /health` route returning `{status, worker, version, enabled, bindings_ok}`; (3) a self-describing header (purpose, capabilities, deploy method, canonical source); (4) a canonical directory in a repository holding a copy of the deployed source, so that repository and deployment can be compared byte for byte; (5) a row in a registry table (`service_registry`: name, purpose, kind, status, crons, dependencies, health URL, autonomy level, responsible role); (6) a list of secret names, never values; (7) kill-switch and autonomy flags readable from a key-value store or database. The registry is the census authority; deployed reality is reconciled against it at an interval (for example hourly) and each member is labelled `live`, `drifted`, `degraded`, `paused` or `retired`. A member lacking a version is invisible to the drift comparison.

### 27.3 Dynamic dispatcher

[0119] On each per-minute invocation the dispatcher (1) reads every row of `fleet_crons` where `enabled = 1` and `next_fire` is null or not later than now; (2) for each row computes the next fire time from its five-field cron expression and inserts a `fleet_runs` row with status `queued`, the task identifier, the cron name and the start time; (3) posts `{task_id, cron_name}` to the executor; and (4) records `last_fired` and the computed `next_fire` whether or not the post succeeded, so that a failing executor does not cause re-firing every minute; a dispatch error is visible as a run row that never leaves `queued`. Next-fire computation: a field matcher accepts comma-separated terms, each `*`, a step `*/n` (true when the value is a multiple of n), a range `a-b` or a literal; starting at the following minute, successive minutes are tested against minute, hour, day-of-month, month and day-of-week, up to one year of minutes (527,040), returning null if none matches. For example `*/10 * * * *` called at 12:03 returns 12:10. Alternatives: a jump-ahead search; a cap of K jobs per invocation with carry-over; a deterministic stagger offset per job; a durable queue between dispatcher and executor.

### 27.4 Executor and run ledger

[0120] The executor reads a task row from `fleet_tasks` (`id`, `type`, `definition` as JSON, `enabled`) and runs it by type: `sql` runs one statement against a named database binding and returns the row count and first rows; `http` issues one request and returns the status and the start of the body; `ai` calls a model through a gateway with a model from an allowed list (default the cheapest, section 17) and a bounded token count; `workflow` runs an ordered list of such steps. Any other type is rejected. The run row inserted by the dispatcher (`queued`) is updated to `running`, then to `ok` with a truncated result or `failed` with a truncated error; a manual invocation inserts its own row. After each completion the executor builds an event envelope (schema version, kind, identifier, timestamp, provenance with emitter, session and a SHA-256 of the payload), validates it by a deterministic validator before writing, and stores it with status `accepted` or `rejected` and the validation error, so a malformed record is rejected at write time. A fuller run ledger has columns `run_id, worker, trigger (cron|http|event|manual), ts_start, ts_end, status, error_class, summary, evidence_refs, parent_run, cost`.

[0121] Accounting invariant. For every batch an executor scans, `executed + failed + needs_human + no_action = scanned`, and a batch violating it is itself a failure. In one recorded case an executor reported "scanned 25, executed 0, failed 0, needs_human 0, no_action 0" while the tracked signals showed one dispatch each, no verification and repeated re-detection; the invariant finds that class of fault mechanically.

### 27.5 Redundancy of two schedulers and the dead-man check

[0122] Two scheduling paths are independent when they share no process and no next-fire state table: 1802 keeps its state in the platform and 1804 in `fleet_crons`. A tick slot has a record when a `tick_runs` row (section 15) or a `fleet_runs` row with a start time inside the slot exists. The dead-man check 1818 performs: step 1820, for each declared recurring procedure compute the expected slots in the last window from its cron expression; step 1822, count records per slot per scheduler; step 1824, a slot with zero records opens an alert work item naming the procedure, the slot and the scheduler(s) that declared it, labelled a stop with the higher priority; step 1826, when both schedulers declare the procedure and exactly one produced a record, a low-priority degraded-redundancy item is recorded and no alert opens. Duplicate firings are harmless because the manager tick takes a work claim (section 13). Example: a `*/10 * * * *` tick has 6 slots per hour; with scheduler A present in all 6 and scheduler B in 5, slot 3 yields only a degraded-redundancy item and B's reliability is 5 of 6. Alternatives: three schedulers with majority; a hot standby taking over when the active scheduler's heartbeat age exceeds a threshold; schedulers on different platforms; an external monitor calling the check's health route; event-triggered scheduling.

## 28. Signal-organism architecture: signals, boundary, triage and re-entry

[0123] In one embodiment the outputs of the system re-enter as inputs. A "signal" is a record s = (time, source, content, weight), the weight stating what the signal licenses the system to believe; a record without a weight is noise. An "open-question set" U(a) is the set of questions from a fixed audit list (for example 15 questions) that an artifact a does not answer. The layers are tables in a chain: L0 intake; L1 triage (a weight and a decision of respond, log or ignore); L2 boundary confinement; L3 synthesis; L4 an ignorance audit; L5 refinement; L6 fitness; L7 deposit with attribution; L8 re-entry of the deposited artifact as a signal. A table `signals` holds `id` (stable hash of source reference and time), `ts`, `source`, `source_ref`, `content`, `open_questions`, `evidential_weight`, `domain`, `status` and `decision`.

[0124] Boundary. A table `signal_worker_boundary(worker, source, permitted, domain)` with key (worker, source) is looked up before a worker consumes a signal: no row, or `permitted = 0`, denies (default deny); a denial is written as an incident and does not stop the worker's other work; a triple whose domain is not listed is rejected. For example dissemination workers may consume only deposited artifacts and never raw signals. Technical effect: confinement by lookup bounds which worker reads which data class, so a defect or injected instruction in one worker's input reaches only the sources its row permits.

[0125] Re-entry. A scan selects artifacts holding a deposit identity, with distribution status distributed or published, whose identifier is not already the `source_ref` of an `artifact_reentry` signal (the identifier is the idempotency key); builds the content from title, abstract, identifier and U(a); writes a signal with weight 0 and status logged when U(a) is empty or unrecorded; otherwise sets a stored weight (high for verified, review-clean artifacts) and writes the signal with source `artifact_reentry`, which flows through triage. A response is accepted only if it strictly shrinks U, and a shrinkage obtained by narrowing a claim (fewer sentences containing a result verb or a number) is logged as a violation and rejected. A fitness threshold (expected reduction in open questions per unit of effort) is initialised to null, with triage falling back to the L1 scorecard until an experiment justifies a value.

## 29. Wiring graph, producer-consumer maps and orphan detection (FIG. 19)

[0126] A "wiring graph" is a directed graph whose nodes are fleet members and stored resources and whose edges are declared bindings read from the platform's deployment metadata, not from documentation. An "island" is a worker with no service edge in either direction, a "sink" one called by others that calls none, and a "source" one that calls others and is called by none. A "producer-consumer map" lists, for each table or queue, the processes that write it and that read it.

[0127] Referring to FIG. 19, a wiring sweep 1904 calls the platform scripts interface 1902 and records for each worker its cron expressions, routes, queue consumer bindings and bindings by type (relational database, key-value namespace, object bucket, vector index, queue, durable object, workflow, service binding naming the target worker, AI binding, secret name and text variable) in a graph store 1906; a worker for which the interface returned an error is listed under `errors` and excluded from the counts. The graph analyzer 1910 reads 1906 and the registry 1908 and performs: step 1930, build the edge set of (caller, callee) pairs from service bindings; step 1932, compute in-degree and out-degree; step 1934, label islands, sinks and sources; step 1936, label an edge target unresolved when it is absent from both the graph and the registry, and open a work item for each; step 1938, compute directed density as edges / (n x (n - 1)), for example 49 / (80 x 79) = 0.0078; step 1940, report ghosts (registered, not deployed), unregistered (deployed, not registered) and unversioned members; step 1942, write an integration score and the counts to an integration state table. Orphan tables are found by joining each table's writer set and reader set, so a table with writers and no readers (a producer without a consumer, the dominant failure mode of one audit day) becomes a work item instead of a silent backlog. Alternatives: edges weighted by call volume; data-flow edges from shared tables; strongly connected components.

[0128] Fleet runtime census. A table `fleet_worker_census` lists each member with measured daily activity. A member absent from the activity data is labelled unmeasured, not idle (absence may mean absence from the monitor's roster: in one census four of fifteen unmeasured members answered a health probe), and a member is retired only after the monitor roster has been extended to cover it and it is shown dead for a period (for example 2 days) or firing and failing; low-traffic hubs are folded into a hub that already serves them.

## 31. Objective space and self-authored goals (FIG. 20)

[0131] This section describes how the system originates its own goals without altering the objective the principal set. An organization run by agents either proposes nothing beyond its charter, leaving the principal as the only source of direction, or rewrites its own objective, which is silent objective drift; the mechanism separates instrumental goals, which the system may author and adopt, from the objective, which it may only propose to change. "Objective" means a terminal statement of purpose or an objective function (for example a mission and weights over metrics). "Ratified objective" means an objective row written only by the principal or a ratification action of the principal, never by an agent. "Goal" means a falsifiable, reversible instrumental statement of what to do next, evaluated against a ratified objective; a "derived goal" has a recorded parent ratified objective and a "novel goal" has none and enters probation. "Objective space" means the set of ratified objectives (standing), derived goals and novel goals on probation, held in one record set showing which statements direct the system and with what authority.

### 31.1 Records

[0132] In one embodiment a table `objectives(id, kind, statement, version, status, ratified_by, ratified_at)` holds ratified objectives and is writable only by an insert-if-absent seed routine and a ratification action; a table `goals(id, statement, goal_type, parent_objective, alignment, score, priority, dod, program_code, owner, status, adopted_at, retired_at, retire_reason)` holds authored goals, where `goal_type` is `instrumental` or `objective-revision`, `parent_objective` is null only for novel goals, `alignment` states why the goal serves its parent, `dod` is a falsifiable definition of done and `status` is one of proposed, adopted, active, probation, superseded and retired; and an `objective_space` view presents the union with a tier column.

### 31.2 Authoring cycle (steps 2002 to 2028)

[0133] An authoring worker runs on a schedule (for example daily, `0 2 * * *`). Step 2002: gather bounded signals (for example 50 rows each) from the objectives, idea proposals, self-questions, autonomy score gaps, self-heal actions and rows of the inferred-direction table (section 34.3); a failed read yields an empty set, not an aborted cycle. Step 2004: a model-backed agent synthesizes falsifiable goal statements, each with a definition of done that a probe can check; only the answer field of the model response is parsed, fenced JSON is stripped and an empty answer emits a warning receipt so that a silent model failure is visible. Step 2006: classify each candidate `instrumental` or `objective-revision`; a candidate that would change the mission, the weights of the objective function or the boundary of residual consent is an objective revision. Step 2008: every objective revision is written with status `proposed` into a ratification queue with a principal-ratification role and is never adopted by the authoring worker; a code branch converts any attempt to give it status `adopted` or `active` to `proposed`, and an event `objective-revision-proposed` surfaces it in the principal queue (section 14).

[0134] Step 2010: score and de-duplicate. Each instrumental candidate receives a score in [0, 1], for example 0.4 x falsifiability + 0.4 x leverage + 0.2 x novelty, each a model score against a stated rubric. Step 2012: a candidate is rejected, with its score recorded, when the score is below a threshold (for example 0.5) or when its token set A has Jaccard similarity |A and B| / |A or B| or containment |A and B| / min(|A|, |B|) at or above 0.6 against any goal B adopted in the last 30 days; tokenization lowercases, removes stop words and stems. Example: a 10-token candidate sharing 6 tokens with a 14-token adopted goal has Jaccard 6 / 18 = 0.33 but containment 6 / 10 = 0.6, so a reworded duplicate that a Jaccard-only or exact-hash test would admit is rejected. Step 2014: anchor the candidate to a ratified objective it serves by a stem (prefix) match of its statement against the objective's statement and the program's keywords; a stem match is used because a whole-word expression for "topolog" fails on "topological". Step 2018: a candidate with a parent is adopted as a derived goal with `parent_objective`, an `alignment` sentence and a definition of done, at most N per cycle (for example 3), highest score first. Adoption also writes a row to a drainable ledger (for example `task_dod_register` with a due date) so that the goal has a consumer, and a research-type goal is written to a research queue from which a triage worker carries it to publication (step 2020).

[0135] Step 2016: a candidate that passes the score test but has no anchor is a novel goal, stored with status `probation` and a review deadline (for example 14 days), not dispatched to executors with write authority, and counted past its deadline by a metric (`objective_space_novel_overdue`). At step 2024 the principal or a delegated ratification role ratifies or declines it; a ratified novel goal becomes standing at step 2026 (written into `objectives` by the ratification action, able to anchor later goals, and depositing trust under "objective space extended", section 24.3); a declined or overdue goal goes to step 2028. Step 2022: a goal is retired when its definition-of-done probe passes, when it has been active longer than a stale limit (for example 14 days) without evidence, or when a newer goal supersedes it; retirement sets `retired_at`, a `retire_reason` and status `retired` or `superseded` and cancels its ledger rows, so that no goal leaves the active set without a disposition.

### 31.3 Guards and alternatives

[0136] The mutation endpoints of the authoring worker require an authentication header and return an unauthorized status without it. Invariants enforced in code: (a) the authoring worker never mutates the objectives table; (b) an objective revision cannot reach an adopted status; (c) an adopted goal has a non-empty parent and alignment. A weekly value-proposal loop may author proposed revisions of the objective function under the ratification queue, whose adoption remains with the principal. Technical effect: new, ranked, de-duplicated work at a bounded rate without a human authoring step per goal and without any path by which an agent alters the objective. Alternatives: anchoring by embedding similarity (for example 0.75); auto-ratifying a novel goal after a named metric improved over a control window, never an objective revision; per-tier adoption caps; per-program authoring with the program charter as parent; ratification by a quorum.

## 32. Work breakdown structure and agent protocol (FIG. 21)

[0137] A work breakdown structure gives every unit of work an address that persists across sessions, agents and stores. "WBS code" means a dotted identifier `<portfolio>.<program>.<project>.<phase>[.<task>[.<subtask>]]` (for example `PRG1.PRG2.002.P4`). "WBS item" means a work item carrying a WBS code or roadmap identifier, a responsible role, one or more trigger identifiers (other items or named gates that are done before the item is ready), a done check and a milestone. "Hand-off" means a recorded change of the responsible role for an item.

### 32.1 Addressing and plan convention

[0138] In one embodiment the program level is a controlled vocabulary of codes, each with a repository, branch prefix and plan prefix; branches follow `{program}/{type}/{slug}` with a work type from a fixed list (paper, audit, artifact, infra, fix, kaizen); a phase is one of ten codes P0 to P9 (initiation through extension). Every step of an agent's plan is prefixed by the full code to phase level in square brackets, and its status reflects the item's actual state; a code absent from the registry is a defect. On meeting a code a processor (1) parses program, project and phase; (2) selects the `program_registry` row (wbs code, phase, current version, status, knowledge-graph node, update time); (3) loads the project plan, a version file and artifacts; (4) queries the knowledge graph for what the item depends on and what depends on it; (5) flags a version-file mismatch with `current_version` for reconciliation before execution; and (6) executes, then verifies by re-selecting the registry row and confirming the graph edges, a storage claim without a re-select being a "phantom claim". A pipeline loop advances each active row below P9 by one coded phase, and a dependent of a changed project receives coded P9 steps for detect, impact, update, rebuild and republish. A delegation prompt carries the WBS code and a typed role (explorer, implementer or reviewer), and the hand-off is a row in a claims table (section 13) so a second doer cannot take the same item.

### 32.2 Item state machine (FIG. 21)

[0139] Step 2102: Backlog: an item is created with an identifier, a responsible role, trigger identifiers, a done check and a milestone. Step 2104: the item is ready when every trigger names an item in state Done or a gate that is open; otherwise it moves to Blocked (2116) with the blocking identifier recorded, else to Ready (2106). Step 2108: In progress: a doer in the responsible role claims a Ready item; the claim is released after an idle expiry (for example 24 hours without a recorded action) and the item returns to Ready; an item whose next step is identity-bound is placed in the principal queue (2120) with a default, a reason and a closing probe. Step 2110: Review: the doer asserts done and hands the item with evidence to a reviewer role that is a different executor, in one embodiment of a different model family. Step 2112: the closing probe named in the done check runs; a pass moves the item to Done (2114) with evidence stored, and a failure returns it to In progress and increments a rework counter, an item at or above a threshold (for example 3) being escalated as a root-cause item (section 6). Step 2118: an item leaves the active set only as done, superseded or cancelled, each with a reason. Step 2122: on Done, items naming this identifier as a trigger are re-evaluated and a Blocked dependent whose triggers are all Done moves to Ready. Alternatives: states as labels on a mirrored tracker or as a transition log (`from_state`, `to_state`, `at`, `by_role`, `evidence`); dependencies as graph edges so propagation reaches transitive dependents; triggers combined by AND or OR; time triggers.

## 33. Project management practice

[0140] In one embodiment the canonical state of programs, projects and tasks lives in a relational database and a project board mirrors it one way, database to board, except by explicit principal action. On a state change (phase transition, status update, publication, session closeout) the processor updates the mirrored issue's labels, milestone and body or creates one from a template matching the record type, adds a sync label and writes an audit row; comments, reviews and board positions are not synchronized. A label taxonomy maps program labels to program codes, status labels to database statuses and milestones to sprints or releases. Technical effect: one canonical record with a one-way mirror avoids split-brain edits, and the audit row shows what was mirrored and when.

[0141] Milestones group items by urgency or gate, for example Now, Next (after the item's trigger), After filing (gated until a gating event, by a gate label) and Later; an item's milestone changes only on its own state change or a manager's recorded action. A project is stalled when it has open items, no item changed state in D days (for example 14) and no claim is held; each stalled project adds 2 to the risk value of section 5 and raises the verdict to AMBER, and the manager's response is a recorded action (reassign, split, set an explaining trigger or supersede). The definition of done is the multi-path definition of section 26.1. The organization's own launch roadmap uses the same shape: each row has an identifier, title, responsible role, trigger, done check, milestone and status; a generator writes one file per row and a script creates labels, milestones, issues and boards from them; a closed item files a plus issue from a reserved share of capacity; items only the principal can do are marked with what the system prepares so the principal's part is a click, a signature or a decision, ordered by their triggers. Technical effect: a plan expressed as items with triggers and done checks lets a processor compute ready work (section 32.2) and diff a bootstrapped plan (section 19A) against a hand-written one field by field.

## 34. Experiments, roadmap proposals and inferred direction

### 34.1 Experimentation program

[0142] "Experiment" means a registered comparison of a treatment against a control on a named outcome metric over a fixed window, held in a registry (`id`, `name`, `hypothesis`, `kind`, `treatment`, `control`, `outcome_metric`, `baseline_date`, `status`, `owner`) with daily counts per exact path in a statistic table. Measurement rules: (a) a platform's own invocation counts are self-health, and honest signal is exact-path requests net of scanner traffic or external view and download counts; (b) when one signal is too small to reach significance, at least two independent signals are combined or the window is extended (for example at 3 versus 4 requests a day, a 14-day difference of 14 is only 14 / sqrt(42 + 56) = 1.41 standard errors); (c) results are read from the stores, never supplied; (d) treatment and control are measured over identical calendar windows. Stop rules: the experiment stops on the first of (1) the window closing (for example 14 days), (2) a guard metric breaching, (3) futility, when the sample needed for the target power exceeds a cap (for example 60 days), and (4) a principal stop through a configuration row. A treatment with a positive delta on at least 2 metrics is promoted to standard operating procedure for its surface; otherwise it is dropped with a rationale written to the registry. A suggestion surface may rank candidates by a bandit drawing from Beta(1 + clicks, 1 + impressions - clicks), rewarding a successful use rather than a click.

### 34.2 Roadmap proposal and trusted sources

[0143] A roadmap proposal (section 5, step 314) is parsed from fields TITLE, WHY, code-task, code-anchor and EDIT, and is rejected unless (a) the target path is outside control-plane, governance and separated-plane paths, (b) the anchor is at least a minimum length (for example 20 characters) and occurs exactly once in the target, and (c) no proposal with the same normalized title is open or was closed in the last 30 days. A validated proposal becomes a work item whose `source` is checked against a trusted-source list, which decides whether it may take the merge-on-green and canary path; any other source requires review. A daily cap bounds origination.

### 34.3 Inferred direction from revealed preference

[0144] "Revealed preference" means direction inferable from choices the principal made and avoided, as distinct from stated objectives. At each tick (after recognition and before the queue pull) the processor counts, per issue category, the items the principal filed in the last 7 days; a category with 2 or more is written to `inferred_direction` with a confidence, for example min(1, 0.1 x count), and the queue score of its items is multiplied by (1 + confidence) (for example 3 filings in `site` give 0.3, so a base score of 18 becomes 23.4). Rows leave when the window no longer holds 2 items. The inference changes order only: it raises no authority, changes no limit and alters no ratified objective. A completed item in an inferred category records "inference acted on correctly" in the trust ledger unless the principal reverses it ("inference misread"); `inferred_directions_unacted` counts directions with no pulled item; and a stable direction may seed a goal candidate at step 2002. Technical effect: work order follows the principal's behavior without a questionnaire and without self-granted authority, as inspectable rows with an expiry. Alternatives: preference drawn from items closed or reopened, edits to agent output or gate cards approved quickly; exponential decay; direction per board member with agreement of two.

## 35. Cost-optimized routing stack (FIG. 22)

[0145] This chapter extends the model ladder of section 17. A "task class" means a named category of work (for example classification, extraction, digest synthesis, an agent loop with tool calls, code writing, reader-facing drafting) for which one capability test and one validation rule are defined. A "model rung" means one entry in an ordered list of ways of producing an answer for a task class, from no model call to a frontier model. A "capability canary" means a short deterministic test of a model for a task class returning pass or fail. "Cost per verified outcome" means the spend attributed to tasks of a class divided by the number of those tasks that passed validation, as distinct from cost per token. "Resolved upstream" means the model that actually served a request after alias, router or gateway indirection, as logged per request. Technical effect: spend on a model-backed fleet is dominated by repeated context and retries rather than the token price of one call, so routing by capability first and price second, with a deterministic verifier deciding escalation, lowers cost per verified outcome without lowering the pass rate, and a cap with a free fallback keeps a budget breach from stopping work.

### 35.1 Rung definitions

[0146] In one embodiment the ladder has eight layers, descended in order, each entered only when the layer above cannot answer or failed a measured check; at step 2202 of FIG. 22 a task is received with its task class. L0, deterministic handler (steps 2204, 2206): if the answer is computable by a query over the ledgers, a regular expression, a probe, a static lookup or a template fill, it is returned with no model call. L1, cache (2208, 2210): an exact response cache with a time to live, a key-value match for idempotent queries, a semantic cache with a cosine threshold and stable prompt prefixes billed as cached input, a cached answer being served only if not invalidated by a change to its source. L2, capability gate (2212): only models whose canaries passed for the class are kept, price being a tiebreaker and never the gate. L3, cascade (2218 to 2222): free tier, then a cheap paid model, then a frontier model, moving on only on a measured failure. L4, ensemble: N samples or propose-then-aggregate, only when the components are free or cached. L5, distilled specialist: a small model or exemplar bank trained offline on frontier trajectories for a recurring class. L6, draft then verify: a cheap model drafts and a frontier model repairs only when deterministic checks fail. L7, budget scheduler (2214, 2216): per-tier daily caps, an organization ceiling, a stated degradation order and a free fallback. For classes under a frontier-only model floor (section 36) the ladder reduces to L0 to L2 and L7.

### 35.2 Capability before price

[0147] An agent or coding loop requires valid structured tool calls, and a cheaper model that does not emit them costs more through retries and truncation than the model it replaces; in one implementation four candidate models did not emit tool calls for an operations loop, so routing by price alone silently broke the loop. The system keeps a capability matrix `model_task_matrix(task_class, rung, model, unit_cost, canary_tool_calls, canary_schema, ctx_tokens, max_out, agreement, admitted_at, probed_at)` keyed by (task_class, rung, model), where `model` is the resolved upstream identifier, the canary columns hold 1 (pass), 0 (fail) or null (untested) for tool-call validity, schema conformance and context size, and `agreement` is the label agreement of section 37 where a gate applies. The router selects, from rows of the class with all canaries passing and agreement at or above the class gate, the lowest rung (equivalently the lowest recorded cost among passing models); alternatively expected cost per verified outcome (unit cost times mean tokens divided by pass rate) orders them.

### 35.3 Cascade, verifier and escalation rules

[0148] Escalation (step 2222) is triggered only by a measured signal recorded in the attempt row: a schema or validator failure, a tool-call parse failure, empty content, truncation by length or a confidence below a threshold. A deterministic verifier (tests, schema validators, unit checks) keeps the cascade cheap because it needs no second model call. Steps: return a deterministic answer if one exists (2204, 2206); return a valid cache hit (2208, 2210); take the passing rungs (2212); if a class or organization cap is breached, step to a free or cheaper rung and log the step-down (2214, 2216); run (2218); verify (2220); on failure increment attempts and move one rung up (2222), failing the task to a work item after MAX_RETRIES (for example 2) or at the last rung; record cost, rung and attempts (2224). Example (illustrative): of 100 tasks a cheap model at 0.002 passes 60 and a frontier model at 0.02 passes 98; the cascade spends 0.2 plus 0.8 for 99 verified outcomes, 0.0101 each, against 2.0 / 98 = 0.0204 for frontier only, with an escalation rate of 0.40. Alternatives: self-consistency voting among free samples; a learned router.

### 35.4 Caps, graceful degradation and the free fallback

[0149] Each task class and the organization have a daily cap and a monthly ceiling, enforced both by the router (spend in the gateway log joined by task) and by the platform gateway (a spend limit). The degradation order is: serve from cache; step to a free tier; step to a cheaper paid rung; queue the task for the next window. A paid-path failure or a cap hit does not end a task while a free path exists. A cost guard is installed only after the resolved upstream of the path it guards is probed, because a guard whose target is dearer than the status quo raises cost, and no routing or cost change ships without a same-turn probe of the logged resolved upstream rather than the model constant in code.

### 35.5 Context economics and measurement

[0150] Repeated contexts of 130,000 tokens or more were observed to dominate input cost. Levers in order: stable-prefix caching; compaction of old turns; structured conversation state in the database with a summary re-injected in place of raw history; retrieval of relevant slices; and a bounded size on every tool result, so input tokens per round stop growing with turn count. Measurement is per task class, joined on the gateway log (including upstream model and job identifier): cost per verified outcome; escalation rate (share of tasks reaching the last rung); cache hit rate; tool-call validity rate.

## 36. Model floor and model standards gate (FIG. 23)

[0151] "Model floor" means a minimum capability standard a model must meet before it may be routed to a class of work, enforced by a scan of source and deployed artifacts; "model standards gate" means a minimum context window and maximum output applied to every model advertised to or configured by any client, with a registry of exemptions. Both are enforced by guard programs, so that a purge of a disallowed model is not reverted by a concurrent deployment.

[0152] Model floor. A tenant policy may require that a model that writes or executes code, or that produces reader-facing output, be of a frontier class, with a configured banned list of named small, legacy, distilled, small mixture-of-experts or quantized variants for the task classes the policy names. Field justification: a quantized fast model used to audit published research invented author attributions, and a small mixture-of-experts code path did not hold an iterate-and-repair loop. Enforcement, on the guard cadence: (a) enumerate repository sources of every worker and fetch each live deployed bundle through the platform interface; (b) strip comment-only lines and the banned list's own declaration, and skip lines carrying a history marker; (c) match the remaining lines against the banned patterns; (d) exit 0 if none match, otherwise exit 1 and file a work item per worker with the matching line. Scanning deployed bundles as well as sources catches a purge reverted by a concurrent redeploy.

[0153] Model standards gate. Every model advertised to or configured by a client carries a maximum output of at least 32,768 tokens and a context window of at least 128,000 tokens; a model that cannot meet the floors is retired from the catalog or registered in an exemption registry with per-model evidence of the platform-native cap, and silent noncompliance is a hard finding. Verification after every model change: (e) read each server's health version and deployed bundle and check the constants for default maximum output, answer cap, reasoning cap and context; (f) read back per-model maximum output from each client store; (g) run a catalog guard comparing each entry to the registry and checking that every internal model appears; (h) record a claim-sheet row. A retry halves a requested ceiling when the platform rejects it, and a model listing advertises honest values only. A model is eligible for a class only if it is above the floor, meets the gate or is exempt with evidence, has passed the class canary, and, for a class used as a gate on the organization's decisions, meets the agreement threshold of section 37.

## 37. Fleet calibration and model admission (FIG. 23)

[0154] Infrastructure calibration. In one embodiment a calibrator worker runs daily, weekly (adding an adversarial input battery, burst concurrency and plan-weight tuning) and monthly (adding retention cleanup), probing services, the database, the object store and the vector index with self-generated traffic that is never counted as external usage. Each run writes a verdict score from completeness, integrity and plausibility checks, and a simulate mode injects an extreme input to show the detector fires. Baselines are exponential moving averages with variance-adaptive thresholds (for example mean 120 ms and deviation 15 ms give a threshold of 165 ms). Autonomous adjustments are limited to an allowlist of reversible actions (tune-threshold, tune-plan, publish-config, retention-cleanup), each with before and after values, verified on the next run and reverted with an audit row if the metric regressed.

[0155] Prediction calibration (extends section 8). Stored predictions carry a stated confidence p. At scoring they are grouped into confidence bins per decision type (for example 0.5 to 0.6 up to 0.9 to 1.0) and each bin's hit rate h is computed; calibration error is the count-weighted mean of |p - h| and a Brier score the mean of (p - outcome)^2. The confidence cap of a decision type (the highest stated confidence it may carry when gating autonomous action) is lowered by the bin's gap: 40 predictions in the 0.8 to 0.9 bin (mean 0.85) matched 28 times give h = 0.70, lowering the cap by 0.15. Technical effect: a stated confidence that gates autonomous action is replaced by an empirically corrected one.

### 37.3 Model-admission pipeline

[0156] The pipeline runs per (candidate model, task class) and is the path by which a row enters `model_task_matrix`. Step 2302: a candidate is proposed by a person, a capability scan or an escalation analysis. Step 2304: the floor check of section 36 (not banned; context and output limits met or exempt with evidence), a failure being rejected at step 2306 with the reason. Step 2308: capability canaries (tool-call validity, schema conformance, context size) against fixtures of the class. Step 2310: label agreement: a stratified sample of N questions (for example 100 to 500) is drawn from the organization's labelled store, the candidate answers each, and agreement (matches / N) and a lower confidence bound (for example a Wilson 95 percent bound) are computed; a sample under a minimum (for example 30) returns inconclusive. Step 2312: the lower bound is compared with the class gate (for example 0.6 to 0.85; in one measurement a candidate agreed in 0.17 of cases against a gate of 0.7, near the random rate, and was not adopted). Step 2314: on failure the model is rejected for that class with its agreement stored, remaining eligible for other classes. Step 2316: on success a rung row is written. Step 2318: monitoring by scheduled canaries, baselines, cost per verified outcome and a shadow sample in which a fraction (for example 5 percent) of production decisions is also labelled by a person or a stronger rung to compute rolling agreement. Step 2320: when rolling agreement falls below the gate minus a margin (for example 0.05), a canary fails twice in a row or the floor list changes, step 2322 demotes or removes the row, routing reverts to the next passing rung, an audit row records the reason, and the model may re-enter at 2302. A table `model_admission(id, model, task_class, stage, n, agree, lower_bound, gate, decided_at, reason, evidence)` records each stage (floor, canary, agreement, admitted, demoted, rejected). Alternatives: agreement per question class; admission by a judge of another model family with a human check on a sample; cohort rollout; a gate on calibration error.

## 38. Executors, code-only mode and per-executor trust

[0157] "Executor adapter" means a module presenting an executor of any kind through one interface: describe() returning capabilities, supported task classes, model, cost class and trust key; claim(item) taking a claim per section 13; run(item) returning a result envelope with evidence; and report() writing outcome, cost and duration. Kinds include (a) an open model on the platform driven through a tool loop of the executor of section 27.4; (b) a hosted coding agent that opens pull requests, mapped by an adapter that creates the work as an issue with the doer line and takes a claim on the path; (c) an interactive session of a person or coding assistant, which acts only as an ordinary claimant and which no scheduled step waits for; and (d) a container executor running the same worker code under a job scheduler. All kinds write through the canonical change path of section 12, so the claim fence rejects a stale holder of any kind. The dispatcher reads queue items in priority order, keeps adapters whose describe() lists the item's class and whose rung is at least the item's required rung, orders them by cost class and dispatches the first available; if none qualifies, the item stays queued with a reason and is not handed to the principal unless identity-bound.

[0158] Code-only execution mode. An endpoint serving chat, operations and code from one route classifies each request as code, ops or chat by a deterministic function with no model call, applied to the last user turn and never to injected system context: code signals (intent phrases such as run, implement, fix this code, debug, refactor, write a test, deploy; code fences, imports, keywords, file extensions; an explicit domain hint) are weighted and threshold-gated, ops signals are tool and resource names, and the default and the ambiguous case are ops or chat, because a code request misrouted to ops still works while the converse breaks memory and conversation pipelines. Code requests go to a code model with a code-only contract and toolset (run-code, workspace read, write, list and delete, repository read, file write and pull request, web fetch and search; operations tools excluded); the class is logged per request. Under the contract the executor runs only on the server side in an isolated runtime with an object-store backed virtual workspace, never emits code or tool payloads for the client to run, loops plan, write, run, verify and report in one turn, returns executed results first, and attaches actual output to every claim of done; so a client that cannot run code is still served and the mode runs from the scheduler, queue and claim ledger with no person present.

[0159] Per-executor trust adds the executor as a third key to the trust of section 9: `executor_trust(executor_id, surface, action_class, ok, fail, trust_score, ladder_position, refreshed_at)` with trust_score = (ok + 5) / (ok + fail + 10). A new executor starts at the prior and earns scope on its own record (for example ok 6 and fail 2 give 11 / 18 = 0.61). The effective rung of a dispatch is the minimum of the executor's rung and the (surface, action class) rung, so a trusted executor does not widen a distrusted surface. A model removed at step 2322 has its executor rows frozen, not deleted. Alternatives: a lower confidence bound; decay toward the prior while idle; trust transferred between versions of one model family at a discount.

## 39. Audit-and-act procedure with verification, correction and capstone documents (FIG. 24)

[0160] "Audit-and-act procedure" means a repeatable procedure in which an audit agent reads live state of a managed system, records numbered findings, acts on findings that survive re-testing and records the outcome of each action. "Finding" means a record having an identifier within the audit, a claim, evidence (a query, probe result or source-file hash, with the time it was read), a falsifier (an observation that would show the claim false) and a state (`open`, `verified`, `corrected`, `retracted`, `pending` or `closed`). "Verification document" means a document that re-tests each finding of an earlier one by an independent path; "correction document" one that supersedes a named part of an earlier one, stating what was claimed, what test showed it wrong and what still stands ("retraction" when it withdraws a finding in full); "capstone" one stating the structural cause shared by several findings. "Measured clock" means a timestamp read from the managed system in the same statement or call that produces the evidence, as distinct from a clock value assumed by the agent. Technical effect: because each finding carries a falsifier, is re-tested independently and is superseded rather than overwritten when wrong, the trail reports the audit's own error rate, and downstream actions (closing tickets, deploying, retiring workers) are taken only on findings that reproduced.

[0161] FIG. 24. At step 2402 the audit agent reads live state (for example queries over alert, event, issue, queue and probe tables, service-binding health probes and hashes of canonical against deployed source) together with a measured clock (for example `strftime('%Y-%m-%dT%H:%M:%SZ','now')`); a timestamp bearing an offset is converted before use. At step 2404 it writes one numbered finding per claim with evidence, evidence read time, falsifier and state `open`. At step 2406 a verification document, by the same or another agent (in one embodiment a model of another family), re-tests each finding by a path chosen so that a shared fault cannot produce the same answer (a source claim against live database state; a database claim against a second table or a probe). At step 2408 each finding is set `verified` or not reproduced; a non-reproduced finding proceeds at step 2410 to a correction record that identifies the superseded finding, retains it unedited, quotes the claim and states the control observation that falsified it. A reproduced finding proceeds at step 2412 to action (a source patch, a tombstone removing a shadowing source, a dispatch, an in-place annotation preserving the original value, a registry change). At step 2414 the realization gate of section 40 tests whether the effect was observed; if not, step 2416 sets the finding `pending` with the deciding query and the earliest time it can decide, and the loop returns to 2406 then. If observed, step 2418 writes a capstone grouping findings by structural cause and checks the cause against independent rosters (section 42.3), and step 2420 feeds the failure modes into the register and the reconciliation of FIG. 25. A database embodiment stores `audit_finding(audit_id, finding_no, claim, evidence_query, evidence_read_at, falsifier, state, superseded_by)` and `audit_document(path, kind, supersedes, created_at)`, kind being audit, verification, correction, retraction or capstone.

[0162] Examples from one audit. (A) A worker emitted alert rows at 2 to 7 an hour although canonical source declared a deduplicating version; a query for a table that version creates returned `no such table`, proving the deployed build predated the fix. (B) A claim that a monitor had been silent for 69 minutes was retracted: the agent had read a header `15:16 (UTC+02:00)` as UTC; the measured gap was 13.65 minutes, one normal interval, and a request to the monitor's refresh route advanced its state, which gave rise to the measured-clock rule. (C) A claim that a prober had died was corrected to a coverage collapse: one writer continued, but distinct probed names fell from 81 to 10 per hour at a discrete transition. (D) The obvious fix for (C), deploying the repository's probe registry, was shown by set difference against the deployed registry to remove measurement of 13 workers carrying 4,372 of 8,698 measured requests a day (50.3 percent), so the deployed registry was taken as base and the missing probes added back with before-and-after checks. (E) An executor reported "scanned 25, executed 0, failed 0, needs_human 0, no_action 0", giving the invariant of section 42.1. Each correction would otherwise have driven a wrong action: retiring a healthy worker, deploying a registry that blinds half the traffic, or registering a worker the fleet had retired. Further errors found the same way include a `LIMIT` that truncated a table, timestamps stored in two formats whose separator sorted differently and excluded every row of a producer, and an absolute claim ("no deploy route exists") disproved by reading the resolver.

## 40. Map-territory realization gate and blocker red-team (FIG. 24)

[0163] "Map" means the representation of the managed system held in a repository, registry, staged patch or document; "territory" means the state read from the running system. "Realization gate" means the check at step 2414 that a claimed fix or fact has been observed in the territory and not only in the map. "Claim state" means one of `code-only` (the change exists only in a repository), `staged` (a patcher or tombstone is committed but not applied), `inferred` (the territory shows the effect indirectly) and `observed` (a deciding query reads the changed state in production). "Deciding query" means a statement whose result decides a pending claim, with a pass condition and a fail condition. The gate: (1) each fix is recorded with a claim state; (2) the agent writes a deciding query, a pass condition, a fail condition and a null expectation (what production would show if the fix were absent); (3) a finding closes only when its claim state is `observed`; `inferred` closes with a label identifying the inference and a scheduled re-test; `code-only` and `staged` leave the finding `pending` with the deciding query. For example, a deploy row showing the new version is `observed`, while the absence of failures after a tombstone is only `inferred`, because a stopped scanner would show the same silence; a staged fix's deciding query reads the next drift-report row with pass and fail conditions on its source path. Technical effect: closing items on repository evidence leaves production unchanged and the alert recurs; the gate limits premature closures to labelled inferences with a re-test date.

[0164] Blocker red-team. "Surface" means any distinct path to the same outcome; "blocker" means a claim that work cannot proceed. Before a blocker is accepted: (1) surfaces for the outcome are enumerated (for a deploy: commit to a repository that a scanner reads, a direct deployer call, a command from a machine holding the account credential, a registry insert bringing the worker into scan scope, a staged patcher run); (2) each is tested and the call and response recorded; (3) the blocker is marked proven only when each surface returned a refusal attributable to that surface; (4) otherwise it is marked unproven and the first surface that did not refuse is executed, or a new one constructed; (5) the blocker is stored with the surfaces tested so a later audit can add surfaces. In one audit two of three asserted blockers fell on red-team. A surface is a path to a missing capability and never a second attempt at an action that a permission check, policy or classifier refused (section 23.5).

## 41. Failure mode register, detectors, remediation contracts and loop breaker (FIG. 25)

[0165] "Failure mode register" means a table `failure_modes(id, name, surface, detector_sql, fire_when, severity, contract_id, first_seen, last_fired, status)` of named failure modes, each with a detector (a database statement or probe returning a count, ratio or set), a threshold and a severity. "Remediation contract" means a record attached to an item stating the owner, the doer, the trigger, the closing probe, a retry bound and a deadline. "Outcome bucket" means one of `executed`, `failed`, `needs_human` and `no_action`.

[0166] At step 2502 the register is read. At step 2504 each detector runs on a schedule (for example hourly) and writes one `failure_mode_hits(fm_id, ts, value, expected, fired, evidence)` row whether or not it fires, so that a detector that stops producing evidence rows is itself detectable. At step 2506 a detector fires when its value crosses its threshold. Examples: coverage (distinct names probed in the last hour below 0.8 times the registered names); masked failure (rows with status `ok` whose structured payload has `ok` false or a named exception); unbounded retry (the same target and error repeated without a state change); shadow (two candidate sources for one worker with differing hashes and a stale earlier candidate); unaccounted (scanned minus the sum of outcome buckets above 0); roster (an emitter observed in the alert table absent from the union of the service registry and the live script list, section 42.3); stale predicate (an alarm's population differs from the population it names); and frozen writer. The frozen-writer detector computes the age as the current time read in the same statement minus the newest write time of the table, normalizing timestamp formats first, and fires when age divided by the expected interval exceeds a threshold:

```sql
SELECT (julianday('now') - julianday(MAX(replace(ts,' ','T')))) * 1440.0 AS age_min, 15.0 AS interval_min
FROM fleet_probe_log;  -- fire when age_min / interval_min > 2
```

[0167] Because a monitor cannot detect its own stop, at least one detector is executed by a worker other than the one that writes the table it reads. A detector can itself be wrong (a classifier matching the substring `failed` in `{"failed":2}` where 2 is a count; the corrected classifier matches structured failure), so a detector whose firings are confirmed in under a threshold share (for example 50 percent over 10 firings) is set to probation.

[0168] At step 2508 a firing detector opens a work item carrying a remediation contract, for example `{"item": "queue-version-error", "owner": "queue-agent", "remediation": {"suggested_action": "queue-drain", "doer": "worker-B", "trigger": "on_fire", "closing_probe": "SELECT COUNT(*) FROM version_queue WHERE status='error'", "pass": "= 0", "max_attempts": 3, "backoff_h": [1,4,24], "deadline_h": 72}}`. At step 2510 a remediation consumer picks items in severity order, invokes the doer and books exactly one outcome bucket per scanned item. At step 2512 the closing probe runs; on a pass the item closes at step 2514 with the evidence row and the register is updated; on a fail it is retried at the next backoff step up to the retry bound, after which it is escalated, reaching the interrupt gate of section 9 only if interrupt-eligible and otherwise reassigned to another doer.

[0169] Loop breaker. At step 2516 attempts are counted per (target, error signature); when the count reaches k (for example 3) retries of the target are suspended, a root-cause work item is filed to the target's program and a probe is scheduled at a longer interval (for example 24 hours), a pass closing the breaker and a fail extending the interval. In one audited deploy ledger 51 of 54 failures came from two targets retried hourly (26 and 25 attempts); k = 3 would have avoided 45 of those 51 attempts. Alternatives: backoff doubling to a cap; re-arming when the target's source hash changes; routing to a different doer after k failures.

## 42. Silent-drop reconciliation, integration defects and deploy subsystem audit (FIG. 25)

### 42.1 Silent-drop reconciliation

[0170] At step 2518 each consuming loop reports per run the number of items scanned and the number placed in each outcome bucket, and the reconciler computes gap = scanned - (executed + failed + needs_human + no_action). When the gap exceeds zero, step 2520 opens a silent-drop incident, reopens the scanned items that have no recorded disposition and refuses to close their parent items, because a signal dispatched once and never verified cannot be called resolved. In addition, on each tick each work item that left an active set without a recorded disposition is recorded as an incident and reopened. Technical effect: the absence of an executor becomes a numeric fault that fires on the first run, instead of a loop that reports zero errors while no repairs occur.

### 42.2 Ledger reconciliation (split brain)

[0171] Where several issue stores exist (in one audit six, with 12 open items in the store that operations tools read and 303 in a store they did not), a reconciliation step unions the stores by a declared key, computes a visibility ratio (open items in all stores divided by open items visible to the operating tools) and fires when it exceeds a threshold (for example 2). Related defects found the same way: asynchronous jobs held in a non-terminal state with non-empty responses, remedied by writing response and terminal status in one statement and reaping rows with a response and no update.

### 42.3 Roster reconciliation

[0172] Step 2522 compares rosters: the service registry, the deployed census, the drift scanner's accumulated set and the probe log. A registry-versus-live comparison cannot see a name removed from both, so a worker that emitted alerts every 15 minutes appeared in no list. The reconciliation therefore adds an independent source, the set of distinct alert and event emitter names observed in the last period, and fires on emitters - (registry union live list).

### 42.4 Deploy subsystem audit

[0173] A deployer that resolves the source to deploy from an ordered list of candidates (for example a fresh object-store copy, then a mirror file before the main file in each repository, then a stale copy) lets a stale mirror shadow a fixed main file, so a repository fix never ships; a tombstone at the shadowing path changes which candidate resolves, and the fix is then confirmed by a deciding query, not by a repeated deploy. Before a repository registry is deployed over a deployed registry, the share of measured traffic of workers that would cease to be measured is computed by set difference, and deployment is withheld when the share exceeds a threshold (for example the 50.3 percent of Example D). A registry whose version column holds the deployed version is never written with the canonical version, because that would make canonical equal deployed and suppress the heal.

### 43.4 The seven-step tick

[0180] A worker provisioned with a scheduled heartbeat runs `runTick(db, {config, env, now})` over a handle exposing `prepare(sql).bind(...).all()/first()/run()`, the contract of an edge relational database; the same function runs in tests over an in-memory SQLite shim. It inserts a `tick_runs` row with `steps_total` 7 and runs seven steps in order, each inside a guard; a failing step appends to the error list and creates item `TICKFAIL-<step>-<hour>` (priority 0) through a helper that inserts only a new identifier, the creation being itself guarded because the database may be what failed (with one table dropped in a test, six steps completed and exactly one repair item existed).

[0181] Step 1, reconcile: each item with status done, superseded or cancelled and an empty disposition is reopened and an `outcomes` row with result `silent_drop` is inserted; then open items whose trigger is null or names a done item become ready. Step 2, reap: claims whose `heartbeat_at` is older than the time-to-live (for example 120 minutes) are deleted and their items return to ready. Step 3, probe gates: each open card's probe is split at the first colon; `env` is satisfied when the binding is present in a presence map of booleans, `item_done` when the item is done, `manual` never by the tick; a satisfied card, showing that the principal's step is done, is closed with a time. Step 4, score: each prediction with null verdict whose due time has passed is evaluated by a table of built-in metric functions (`tick_runs_completed_1h`, `items_done`, `open_gate_cards`, `silent_drops_7d`) and operators `>= <= > < =`, storing `hit` if observed op target holds and `miss` otherwise, an unknown metric or operator scoring `miss`, so a prediction cannot stay unscored by naming a metric that does not exist.

[0182] Step 5, accrue trust: outcomes are grouped by (surface, action class) into n, successes (`verified`) and severe (`hidden_failure` or `silent_drop`), and reliability = (successes + baseline x prior weight) / (n + prior weight), for example (successes + 0.5 x 2) / (n + 2), so 10 of 10 gives 11/12 = 0.917 and 3 of 8 gives 0.40. The ledger row is upserted but its rung is never changed by the tick. Promotion is indicated when the rung is below the ceiling of the surface's `max_permission` (none to observed, propose to assisted, execute to self-extending), n is at least a minimum (for example 10), reliability is at least a threshold (for example 0.8) and no severe outcome exists; demotion when the rung is above 0 and reliability is below 0.6 or a severe outcome exists. An indication opens one item `LADDER-<surface>-<action>-<target rung>` requesting a reviewed change to the policy file ("policy pull request merged after review by a different agent"). Technical effect: scope changes only through a reviewed change to a data file; in a test, 12 verified outcomes on a money action opened a promotion only to assisted, the ceiling of a propose surface. Step 6, dispatch: for each role whose `tick_every` divides the tick number and that holds fewer than the WIP limit of claims, the highest-priority ready item owned by that role and not already claimed (`ORDER BY priority, created_at LIMIT 1`) is claimed, set `claimed` and recorded in `dispatches`. Step 7, plus share: over the last 20 done items, if at least 10 exist and the plus share is below half of `plus_share`, a `REBALANCE-<date>` item opens. The tick ends by writing a four-line report to `tick_runs`, and a health route returns the latest row with status 200 when all steps completed and 503 otherwise, so an external monitor can use it as a heartbeat probe. A seed prediction may state that the count of ticks having all steps completed within one hour is at least the number of tick intervals in an hour (6), so one missed tick gives a miss.

### 43.5 Policy file, validator, protocol, tests

[0183] The policy file 2606 holds `interrupt_gate` (the rule and the five card fields), `standing_limits` (platform permission checks, classifier refusals, the secret lock, outreach consent and opt-out, the principal's override, another session's live claim), `trust` (baseline 0.5, prior weight 2, idle decay, and what trust never reaches: platform permissions, secrets, the gate, standing limits), `ladder` (seven rungs, promotion and demotion rules, the ceiling map) and `surfaces`. In one embodiment nine surfaces (repository, runtime, work tracker, internal chat, outreach, DNS, money, legal, secrets) carry 26 action classes; each surface has a `max_permission` and a `start_rung`, and each action class `reversible`, `identity_bound` and optionally `reversible_path`, `denied`, `reason` and `harness_deny` (shell-command patterns). The validator reports a start rung not among the rungs, a maximum permission not in none, propose and execute, a start rung above its ceiling, an irreversible identity-bound action carrying a reversible path, an irreversible non-identity-bound action with neither a reversible path nor a denial (for example a destructive migration carries "export the table to the object store first" and force push to the default branch is denied), and standing limits lacking the platform, the secret lock and the override. A mirror test requires every `harness_deny` pattern of a gated action (for example `Bash(git push --force:*)`) to appear in the agent product's settings deny list. An alternative generates those settings from the policy.

[0184] The protocol file has a managed block with version comments, replaced alone by a synchronizer, and parts covering unchanging rules (record in code, no secret values, accuracy, never swallow an error), the tick, act-verify-report ("a refusal is an input"), claims and handoff (branch `agent/<item>-<slug>`, draft pull request within minutes), item format, review (never one's own work) and plussing; each role file lists what the role owns, its tick, its steps and a "never" list. A synchronization job installs the agent instruction file into the instruction location of each agent product only where the location is empty or carries the seed's marker, re-running across every repository of the organization, and pointer files direct products that read instruction files of other names to the shared protocol. A continuous-integration workflow runs the tests and a credential-free dry-run bootstrap on every change and, on a manual or default-branch trigger, an apply-mode bootstrap with cloud secrets from the host's store; a boot without secrets exits 2 and fails visibly. The tests cover the policy rules, the mirror, idempotence, the absence of planted secrets in outputs, tier selection, each tick step, a dropped table, silent-drop reopening, stale-claim release, gate closure, ceiling-bounded promotion and hidden-failure demotion. Alternatives to the limits of the seed: an executor that calls a model with the role file and item and writes outcomes back; severe outcomes counted over a window (for example 14 days); dated ladder items; a second model provider so reviewer and doer differ in family at the lowest tier.

## 44. Lessons as design rules, the product boundary and product claims as live probes

[0185] Design rules derived from boot tests of an earlier self-booting system, each realized in the seed: the boot never exits (stage and step guards turn faults into items); test the whole chain early (a credential-free dry run on every change); never swallow an error (exit codes checked and error output kept); verify before depending (stage (b) checks tools and inputs); capability from the environment (tier from budget, start rungs from policy); safety is a classification (reversible and identity-bound flags, validator, mirrored deny list, so the gate is testable data); local first, then widen (low start rungs, widening by reviewed change only); nothing is done without a closing probe; and instructions are part of the artifact (protocol, pointers and role files from the first commit, so a cold agent needs no chat history).

### 44.2 Product boundary file and check

[0186] To make a self-governing system separable into a product and its first customer, a boundary manifest assigns each deployed worker to exactly one class: `core` (the product), `app` (an application on it) or `plane` (a separated personal plane that never ships), and lists core scripts, workflows and tables; an `entangled` note marks where core and application share a file. The check: (1) enumerate live workers as repository directories containing a worker entry file and no `RETIRED` or `FOLDED` marker; (2) add a violation for each live worker absent from the manifest; (3) for each manifest worker that is not live; (4) for an unknown class or missing role text; (5) for each listed path that does not exist; (6) count per class and list entangled workers; (7) fail the change, and thereby refuse its merge, if any violation exists. Technical effect: separability is maintained at the change that would break it rather than found by a later audit. Alternatives: classification by directory convention; a class for shared libraries; a dependency check failing when a core worker imports an app worker; classification of tables.

### 44.3 Product claims as live probes

[0187] Each claim a product page makes is a row of `product_claims(id, product, sort, claim, probe_sql, evidence_note, created_at)`. The probe is a single read-only SELECT returning `expected` (`ok`), `observed` (`ok` or a failure phrase) and `detail` (a sentence with counts), and a gateway rejects any probe that is not one SELECT (a probe containing a semicolon, even in a text literal, is refused) and shows a read failure as its own state. A claims page runs each probe when the sentence is requested for display, and for each claim a remediation contract of class `claim-<product>-<id>` repeats the probe at a stated cadence (for example hourly) with a maximum number of attempts (for example 3) and an escalation target, so a claim that stops being true fails a contract and escalates like any failure mode. Examples: own-work (issues with a code-task line created in 7 days, count above 0); predictions-scored; tick-running (tick rows in the last 2 hours); trust-ledger (latest refresh within 3 hours); failure-detectors; no-silent-drop (silent drops and unrecorded deletes both 0); decisions-logged. A claim and its contract are updated in the same change, and a build fails when claim identifiers named in the boundary manifest differ from those of the stored probes. Technical effect: a sales claim is mechanically tied to data, so a claim that ceases to hold surfaces as an incident.

## 45. Tenant isolation, one-command install, and the product as its first tenant

[0188] Organization-specific work items, role records and tick procedures are stored as data in a database separate from an organization-independent core (persona templates, charter templates, ledger schemas and a probe-and-revert change path), so the method is performed for a new tenant configuration without modifying the core. Isolation levels: level 1, a separate account per tenant with the control plane holding a deployment credential scoped to it; level 2 (default), a separate database and worker per tenant in a shared account; level 3, a shared database with a `tenant_id` column on every core table enforced by row-level policy. A control plane holds `tenants`, `tenant_versions`, `tenant_bindings` and `tenant_caps` but has no read path to tenant items; each tenant pushes an hourly aggregate. A daily isolation probe per tenant pair writes a canary row in tenant A, attempts to read it with tenant B's credentials, expects denial (or zero rows at level 3), deletes the canary and records the result; a mismatch is a severe outcome that opens a priority-0 item and is itself a product claim row. Connector names resolve to tenant-unique environment names, and a test fails if the core contains any tenant's slug or account identifier.

[0189] One-command install. A command taking a slug, a runtime and an idea file runs idempotent steps logged in an installer log: (1) verify preconditions and open gate cards for missing connectors; (2) fetch a signed bundle of the core (a manifest of files, SHA-256 digests, core version and migrations) and stop on any digest mismatch; (3) run the bootstrapper of 43.2; (4) call the provision port of the runtime adapter (section 46) to create the database, apply additive migrations and seed; (5) bind connectors by name; (6) deploy the worker with the schedule and run probes; (7) wait for the first tick and print its report; (8) register the tenant and enable isolation and claim probes. Exit codes distinguish success, a blocked step with items written and a failed bundle verification. Re-running performs only steps whose probes fail, so the same command upgrades a tenant. The product's own roadmap is written as an idea file and run on the extracted core as tenant number one, so the product is the first subject of its own proof, and a defect the tenant finds in the core is filed on the same ledger and reaches all tenants through the versioned bundle.

## 47. Owner console and one-view status

[0193] "Owner console" means a network-served user interface, operated by a principal, that presents the status of every program, project, product and agent of an organization in one view and through which the principal issues commands and answers questions. "Console host" means the edge worker serving the console and its programmatic interface. "Owner card" means a row in the principal queue (section 14) describing one step only the principal can take. "Tap" means one selection of a pre-defined button requiring no typed text. "Credential" means the kind of authority presented with a request: an owner session, a machine loop token or a legacy key. "Step-up" means a requirement that the owner session was verified by a fresh emailed code within a window. Technical problem: status spread over an infrastructure console, a tracker, chat and email cannot be read at a glance, a principal is asked to do work agents could do, and an owner-only control is easy to expose or automate by mistake. The console collects status into one view on the organization's own infrastructure, shows the principal only items that need the principal, and routes every state-changing action through authenticated, audited, allow-listed routes that record which credential acted.

[0194] In one embodiment the home page has a few screens on a static shell (for example Now, Readers and Code), each fed by a small read carrying its own age, and the Now screen opens with a few numbers tied to the principal's goals (for example readers, fleet cost, owner load and reliability). Each read declares its source, lag, authentication and cache in an index row; a content-based ETag excludes time-derived fields so a conditional read returns 304, and a read with a revision parameter returns not-modified, so a status client polls cheaply without false change. The same state is exposed on per-area pages, a changes feed (deploys, issues closed and opened, merges and new owner cards since the principal's last visit), a managers page showing what each manager decided each hour, and a realtime feed whose revision changes when the owner-queue count changes. A "watchmaker index" counts the recurring operations that still need a person or an interactive session: a table lists each recurring operation with a runner, a cadence and a query proving its last run, and an operation whose measurement is missing is listed as unmeasured rather than counted as automated. A triage read maps each breaching metric to its root cause and names metrics mapped to no cause, and a value view shows outputs per unit of spend beside quality. A filing route builds a ticket from a stored explanation of the subject, never from client text.

[0195] Emergency AI control. A control authority holds a paused flag with a revision counter. A pause needs no prior read; a resume requires an explicit confirmation and the expected revision, and the authority applies compare-and-set on the revision (rejecting a mismatch); a repeated pause increments the revision. Before every assistant entry, model call and tool dispatch of an agent process, a fresh check is requested over a service binding whose caller identity is a trusted property of the binding rather than a header, and the dispatch is permitted only on a valid not-paused response. The page shows "AI status unknown" when no confirmation exists, when the last is older than a limit (for example 15 seconds), while a mutation is in flight or on any error.

## 48. Owner authentication, session handling and command execution (FIG. 28)

[0196] "One-time code" means a 6-digit decimal code. At step 2802 the principal types `login` or taps "Email me a code". At step 2804 the console host refuses when the count of codes created in the last hour reaches a first limit (for example 6) or when a code was created less than a minimum gap earlier (for example 60 seconds); otherwise it draws a code from a cryptographic random source, inserts a row with an expiry (for example 10 minutes), stores only `code_hash = SHA-256(code | id | salt)` where the salt derives from a server secret, and emails the code only to one preconfigured owner address held in the worker, never taken from the request; the address is shown only masked and the send outcome is stored. The table `owner_codes` has columns `id, code_hash, created_ms, expires_ms, tries, used_ms, visitor, sent_ok`. At step 2806 the principal submits the code; the host requires 6 digits, refuses when the sum of failed tries over the last hour reaches a second limit (for example 20), reads at most the 3 newest unused, unexpired, sent rows, skips a row whose tries reach a per-code limit (for example 5), compares hashes in constant time and on a match marks the row used by a conditional update on `used_ms IS NULL`, so a code works once even under a race; a miss increments `tries`. At step 2808 a success revokes the previous session, generates a random 256-bit token, stores only its hash in `owner_sessions(token_hash, created_ms, expires_ms, verified_ms, revoked, visitor)` and sets an HttpOnly, Secure, SameSite cookie with a session lifetime (for example 12 hours). A guess succeeds with probability at most 3 x 10^-6, and the hourly cap bounds a hostile hour to about 6 x 10^-5. Technical effect: an owner-only control opens without a stored password, no other address can be allowed, and a leaked row cannot be replayed. Alternatives: a signed link; a passkey; an edge identity gate delivering a signed assertion verified per request against issuer, audience and an owner allow-list.

[0197] Credentials and step-up. The session read returns step-up true when the session was verified within the step-up window (for example 15 minutes). Reads and read-only commands are open; actions need the owner session; destructive actions (marking done or dismissing, ratifying, undo, mutating tools, SQL writes, deploy, merge, mail in the principal's name) need step-up, the page otherwise prompting for a fresh code in place and repeating the tap on verify. The machine loop token may file and clear queue entries for loops but is refused when used to run a console command, approve a decision or hand work back to the fleet. SQL writes exclude DROP, ALTER and REPLACE; UPDATE and DELETE need a WHERE and are first backed up to a backup table; sign-in, claim and budget tables are read-only. Every decision row records the credential.

[0198] Command execution. At step 2810 the principal types into the command line or taps a button; a button is a stored typed command, so typed and tapped commands take the same path, and every state-changing route requires a custom header. At step 2812 the host tests for an owner session. At step 2814 it reads the verb's entry in one command registry in which each verb has a destructive flag, requiring step-up for a destructive verb (step 2822 on staleness). At step 2820 an AI-affecting command passes through the control authority before execution at step 2816. Commands (approve, decline, retry, resolve, close with evidence, call a worker route, dispatch a workflow, deploy, merge, rerun) are parsed in code without a model; a verb is recognized only when it stands alone or names its target, so a sentence merely containing it goes to the model path; no verb executes an arbitrary shell command, and model-callable tools that could make destructive changes on a sentence return confirm buttons behind a fresh code. Plain-English input from the signed-in principal becomes a task for an agent. Voice: a recording of at most a size limit (for example 8 MB) requires the session, is transcribed by a first speech model and on failure by a second, and the text enters the same typed line. Step 2818: each command writes a log row naming the credential. Undo: an agent-authored pull request is reverted on request after a step-up check, and SQL updates and deletes are reversible through the backup table. Alternatives: an explicit inverse for every mutating verb; each owner command filed as a work item with a fenced claim (section 13).

## 52. Self-description record set and honest self-knowledge

[0205] "Self-description" means a machine-readable and human-readable document set, produced by an organization's own system, stating the system's capabilities, limits, access boundaries, governance and current state. "Evidence" for a statement means a probe, ledger query, commit or measured reading that supports it, recorded with the time taken. "Honest-gap list" means the records of what the system cannot do, has not verified or has only described. "Committed copy" means the rendering stored in the organization's repository. Technical problem: an autonomous system that changes itself accumulates drift between the text that describes it and the running system; a new session or tenant starts without knowing what it may do, what exists and what is broken; and statements of ability are asserted without checks, so a system can "know" it can do something it has never done. The mechanisms below give each statement a typed record, a probe or an evidence reference, and a generation loop comparing the rendered text with the running system and the repository.

[0206] Record set. In one embodiment the records are: `capability_ledger(capability, acquired_by, evidence_ref, acquired_at)`, `acquired_by` being construction or delegation and `evidence_ref` resolving to a commit, probe row or ledger row, a capability with an empty `evidence_ref` being rendered in the honest-gap list as "described, not exercised"; `belief_registry(belief, probe_sql, expected, last_observed, last_checked, falsified_at)`; `vocabulary_register`; `objective_space` (section 31); `spof_register(failure, halts_what, mitigation, detector)`; `component_advertisement` (section 18 and the worker contract of section 27.2); `product_boundary` (section 44.2); the autonomy policy and standing limits; `access_map`; `known_gaps(gap, observed_how, owner, closing_probe, opened_at)`; and `product_claims` (section 44.3).

[0207] Statement classes. Class A, measured: a quantity or state, whose evidence is a probe result within a freshness limit (for example 3 hours for a ledger refresh). Class B, structural: a statement about code, files or policy, whose evidence is the result of a deterministic check with the commit identifier at which it ran. Class C, observed limit: the system tried and was refused or failed, whose evidence is the recorded refusal or failure and the path taken (for example sessions unable to create repositories, so per-repository layouts were kept as folders; a classifier denying an action, which the session stated and did not reword). Class D, prophetic: something not built, which carries the label "prophetic", an owner and a trigger. A statement lacking a class or its required evidence is a defect handled by the consistency check of section 53.3. Recording observed limits lets a successor avoid retrying a refused action and distinguish standing limits (policy) from environmental ones (current credentials).

[0208] Beliefs. A belief is a statement the system relies on about itself or its environment, stored with a falsifying probe: a read-only query whose result contradicts the belief when it fails, executed by a probe runner that refuses any statement that is not a single read-only query. For example the belief "ticks run at least every 10 minutes" has the probe `SELECT CASE WHEN COUNT(*) > 0 THEN 'ok' ELSE 'no tick in 2 hours' END FROM tick_runs WHERE started_at > datetime('now','-2 hours')`. When a probe returns other than a passing result, the belief is marked falsified with a time, a work item is opened through a remediation contract, and the self-description renders the belief as falsified until a later probe passes; a probe that errors is rendered as unverified, never as passing.

[0209] Access map and policy as data. The access map lists each surface the system could reach (repository host, runtime account, work tracker, model interface, chat webhook, outreach, domain, payment, legal) with the name of the credential or binding granting it, a boolean `present` determined by testing whether it is set and never its content, the probe used and the time; the renderer refuses any field holding a value other than a boolean, and a repository scan for key and token patterns is a second barrier. An agent thereby learns that a surface is unreachable (and opens a card) without any process handling a credential. The self-description embeds by reference the policy's surfaces with their permission ceilings, rungs, action flags and mirrored deny rules, and the standing limits that outrank trust, so that a session derives for a proposed action the tuple (surface, action class, ceiling, current rung, gate state) by lookup. Where the platform's own checks differ from the policy, the checks win and the description says so. It also states the product boundary classes from the boundary file, the entangled workers and the count of unclassified live workers (expected zero).

[0210] Honest-gap list. Gaps are ordered by consequence; each has an owner, an observed-how and a closing probe that passes when the gap closes (for example six complete ticks within an hour after provisioning), and a gap whose closing probe cannot be stated is recorded as unprobeable and shown to the principal on a card. Technical effect: statements about the system carry their own evidence or their own label; measurable quantities are statements without evidence (target zero), falsified beliefs and their age, gaps without a closing probe, and corrections of the description found by an outside reader.

## 53. Generation, consistency check and amendment of the self-description (FIG. 30)

[0211] A generator, run by the organization's scheduler hourly, on merge to the default branch and on a ledger change event, performs steps 3002 to 3022 idempotently. Step 3002: trigger, taking a lock keyed by "self-description" so two runs cannot write at once. Step 3004: read the ledgers read-only (capabilities, beliefs, vocabulary, objective space, SPOF register, trust summary by surface and action class, the boundary check's output, the policy file, component advertisements and the failure-mode summary). Step 3006: run each record's probe (beliefs, product claims, access-map presence, gap closing probes) through the read-only runner, recording observed value, detail and time, an erroring probe being rendered "unverified at <time>"; a probe the runner would refuse is rejected at assembly. Step 3008: assemble a canonical document (sections in fixed order: identity, what exists, what it may do, what it may not do, what is broken, what is prophetic, how to rebuild; records in sorted key order; timestamps rounded to a freshness bucket) so that unchanged state yields identical text, each statement annotated with its class and evidence, and render it as JSON for agents and Markdown for people. Step 3010: compute a record-level and text difference against the committed copy, a volatile quantity inside a stated tolerance band being bucketed so noise does not churn the repository. Step 3012: the consistency check. Step 3014: on failure the offending statement is moved to the honest-gap list or a work item carrying the statement, the missing evidence and a closing probe is opened; no statement is deleted silently. Step 3016: an empty difference records a clean generation in the tick report (step 3022). Step 3018: otherwise a change is opened on a generator branch with the record-level difference and probe evidence, reviewed by an agent other than the generator (and, where available, a model of another family). Step 3020: on review and green checks the change merges by the canonical path (section 12) and a lineage row (version, parent, changed records, reviewer, merged_at) is appended.

[0212] Two directions of drift are distinguished: a difference arising from the system (a belief falsified, a capability added) updates the repository; a difference arising from an edit to the committed copy that does not match the stored records is not overwritten but reported by a work item with the hunk, because either the edit expresses an intended change to be made through the records or the text is wrong. Alternatives: a generated-only copy checked on each change like a lockfile; hand-edited prose with a generated block between markers. Technical effect: the document is never staler than one generation plus one review interval, and its staleness is stated at its top.

### 53.3 Consistency check

[0213] The check applies rules and collects all violations: E1, every class A, B and C statement has a resolvable evidence reference or probe; E2, class A evidence is within its freshness limit; E3, no field value matches a secret pattern and access-map values are booleans; E4, no class D statement is rendered as a present capability; E5, the embedded ceilings and rungs equal the policy file's; E6, the boundary check has zero violations; E7, every gap has a closing probe or the label unprobeable with a principal card; E8, class D statements name an owner and a trigger; E9, each gated action reachable by a shell command has a deny rule. Rules E5 and E9 tie the description to authority: it cannot say an agent may do more than the policy allows, and it never changes a ceiling, rung or limit, which change only by reviewed change to the policy. A change lowering a statement's class states the reason, and a change to standing limits or the policy requires the principal's approval. Technical effect: an unsupported statement of ability is a failing check, so a claim such as "the system can provision a fresh account" cannot appear in a passing document until a probe supports it.

## 54. Use of the self-description and self-bootstrapping (FIG. 31)

[0214] "Session" means a bounded run of an agent process holding no memory of prior runs. Step 3102: a session starts with only the repository. Step 3104: it reads the protocol file, its role file, the policy and then the self-description. Step 3106: it derives its permission ceilings and rungs per surface, the gates, the standing limits, what exists, what is broken (falsified beliefs, failing claims, open gaps) and what is prophetic and must not be relied on. At step 3108 it reads the access map to learn which surfaces and credentials exist (presence only); when a required surface is missing (decision 3110), step 3112 posts a gate card with the default in effect and a closing probe and the session degrades to the surfaces it has. The session treats the description as data with a freshness stamp and re-runs the probes it relies on when the stamp is older than a limit (for example 24 hours) or a probe in the document fails. Because the description is derived from records it carries no instructions; it is loaded as data and the platform's checks and the policy win over any sentence in it.

[0215] At step 3114 a manager tick (the dispatch of the seven-step tick of section 43.4 or the twenty-step tick of section 24) calls `may(surface, action_class, persona)`, which reads the embedded policy and returns allow, allow with a rung condition, propose only, or deny with a reason; an item on a surface whose current rung is below the needed rung is routed to a reviewer role, and a denied item is recorded with its reason and the next item taken (step 3116), with no retry of the action or a reworded form of it; an allowed item is claimed, executed, verified and recorded with its provenance and prediction (step 3118). A prediction is logged before acting and the provenance records the description version consulted. Because the same data a person reads determines what the tick does, a wrong description produces visibly wrong behavior that a probe catches. At step 3120, bootstrapper stages 1508 to 1514 (section 19A), a new tenant receives a first self-description generated from its own policy, roles, kit backlog and detect results, with an honest-gap list initialized with every stage that has not run (for example "six complete ticks: not seen"), each closed by its probe as stages complete.

[0216] Reconstruction and sync. Because every decision, plan and result lands in the turn it is made as a commit, issue, pull request or database row, a wiped machine is recovered by a new session cloning the repository and performing steps 3102 to 3106; a fresh cloud account by the bootstrapper creating the runtime and re-running insert-or-ignore seed rows; and a lost database by restoring table-only state from backups and repository text by sync. At step 3122 a "sync job" makes two copies of a record agree under a stated direction: tracker to repository (a generated index committed only when changed); repository to database (policy and roles loaded by the reconcile step, the repository winning on difference); database to repository (the generator of section 53). Each sync records the source commit and time, never deletes the destination without a disposition and on conflict opens an item and leaves both copies. The platform's own roadmap may run as tenant number one (section 45), its self-description being that tenant's generated description. Trust events reward honesty: a statement downgraded by the system's own check before an outside reader found it is a clean self-remediation, and one found false by an outside reader is a hidden failure on the surface "self-description". The description can state that a probe passed but not that the probe measures what the statement means, so an outside reader's correction is treated as the strongest evidence.

## 55. Business function chain: registries, dependencies and gates (FIG. 32)

[0217] This chapter extends the organization kit of section 19, the bootstrapping of section 19A and the seed of section 43 from a development platform to an autonomous business system. "Business function" means a recurring kind of work a business needs that has a managing persona, a defined set of output artifacts (an artifact schema), a done check and a gate class; examples are product development, intellectual property, marketing, promotion, events, funding, branding, legal and entity decisions, web presence and reporting. "Function chain" means the business functions of one organization with the dependency edges between them. "Artifact" means a durable output of a work item stored as a file under version control with a registered status. Technical effect: a single idea file is turned, by data and a repeatable planning step, into a dependency-ordered backlog of whole-business work in which each step has a manager, a machine-checkable completion test, an independent review and an explicit point at which a person must act, whereas a model asked to "run a business" without such structure produces unordered, unverifiable and non-resumable output.

[0218] Function registry 3202: a table `business_function(code, title, managing_role, artifact_schema, done_check, gate_class, default_milestone, generic_of)`, where `artifact_schema` is a list of `{kind, path_pattern, required, reviewer_role}` (for the intellectual property function: disclosure, prior-art register, specification, figures, claim strategy, filing checklist, evidence log and a deadline calendar entry, a null path marking an artifact outside the repository closed by a probe), `done_check` is a machine-checkable predicate over the artifact registry, and `generic_of` names a fallback function (section 57.4). Gate class `none` means outputs may be produced and published without waiting for a person; `identity` that finishing the function includes an identity-bound step (a signature, a payment, an account only the principal can hold, an appearance in person); `filed` that the function's public outputs would reveal matter whose protection depends on an earlier act (for example filing a patent application) and wait until a probe observes that act. Classes may be combined, and because the class is data, a tenant whose protective act is a trademark application, a regulatory approval or an embargo date changes a row, not code.

[0219] Artifact registry 3204: a table `artifact(id, function_code, item_id, kind, repo_path, status, evidence, reviewer, content_hash, reviewed_at)`. An artifact is `planned` when the planner creates its row, `draft` when a staff persona commits a file at `repo_path`, `reviewed` when a reviewer of a model family different from the author's records a pass against the content hash, and `verified` when the function's done check holds and the consistency check of section 57.2 returns an empty mismatch list. It becomes `stale` when its content hash differs from the hash recorded at review or when an artifact it depends on changed after the review, and then re-enters review. Technical effect: a downstream artifact (a pitch kit quoting a specification) cannot silently outlive a change to its source.

[0220] Dependency graph 3206: a table `function_edge(from_code, to_code, kind)` with kinds `needs` (the target may start when the source's done check holds) and `gate` (the target may publish only when the source's gate probe holds), for example `IP -> WEB (gate: filed)`, `IP -> PR (gate: filed)`, `BIZ -> FN (needs: entity chosen)`, `IP -> QA (needs: draft)`. A validator run at write time rejects a cycle over `needs` edges and writes a blocked work item naming it. A backlog row 3208 is a work item with `owner_role`, `trigger` (a predecessor item or event), `done_check`, `milestone`, `labels` (for example `role:staff`, `ws:patent`, `gate:filed`), `function_code`, `identity_step` (what only the principal does, or null) and `prepared` (what the fleet prepares so the principal's step is short). Ready test 3210: at each tick the manager selects the highest-priority row for which (a) every `needs` predecessor holds or a narrower trigger item is done, (b) the gate probe of the matching `gate` edge holds if the row carries a gate label, (c) no claim is live on the item (section 13) and (d) the persona's work-in-progress limit permits. A row failing (b) stays in the backlog under its milestone (for example "After filing") without creating an owner card, because nothing is asked of the principal, and becomes ready on the next tick after the probe holds, with no person moving it. Gate probes are ordinary probes (section 8), for example reading a tracker field set on the principal's confirmation, checking for a filing receipt or querying a public status interface, and an unavailable gate probe fails closed. In FIG. 32 the registries feed the function lanes: product development work items 3212; intellectual property artifacts 3214 (disclosure, prior art, draft, claims, checklist, evidence log) leading to the filing gate 3216, at which the principal signs on an owner card and which opens the gated lanes; marketing, promotion, events and the public site 3218; private funding kits 3220 whose submissions are owner steps; the different-family reviewer 3222 that checks each artifact; the consistency check 3224, whose non-empty mismatch list reopens the item; the owner task queue 3226 of identity-bound cards; and the closing step 3228 at which the done check and closing probe pass, the artifact is set verified and trust is updated. Technical effect: the system refuses by construction, without relying on an agent remembering a rule, to produce a public artifact that would defeat a protective filing.

## 57. Review, consistency checks, function artifacts and fallbacks

### 57.1 Review by a different-family reviewer

[0224] Every artifact whose schema names a reviewer role passes review before its status can exceed `draft`. The reviewer is a model of a family different from the model that wrote the artifact; it receives the artifact, the artifacts it cites and the done check, and returns a verdict quoting the passages relied on and a list of defects with severities. The registry records the reviewer persona and family, and a validator refuses a reviewed status when the reviewer's family equals the author's. A defect of at least medium severity reopens the item. The pass is recorded against the content hash, so a later change makes the artifact stale. Technical effect: independent review catches shared-blind-spot errors that same-family self-review misses, and the hash prevents a review being reused for text it did not see.

### 57.2 Consistency check across artifacts

[0225] A function can produce several artifacts that must agree (for intellectual property: the disclosure, specification, figure list, claim summaries, public documentation and pitch material). A QA work item (a) extracts load-bearing statements from each artifact (defined terms, numerals, counts, status labels, dates, thresholds, named components); (b) aligns them by key; (c) lists as mismatches statements that disagree between artifacts, statements required by the artifact schema but absent, and statements whose built or prophetic labels are inconsistent; and (d) passes only when the mismatch list is empty. A mismatch opens a work item on the artifact the schema designates as the source of truth and marks the others stale. Alternatives: extraction by a model whose output is stored and re-checked by pattern tests; alignment by embedding similarity; exact comparison of numbers after normalization. Public-text check: for a function with gate class `filed`, a scan of the organization's public surfaces fails when a term of a mechanism deny list appears before the gate probe holds, so an agent that does not remember the rule is still stopped.

### 57.3 Function artifacts

[0226] Intellectual property function: an invention disclosure; a prior-art register (one row per reference: what it teaches, how the disclosure differs, which claim families carry the difference, and the register's stated limit); a specification with figures having reference numerals and claim-style summaries; a claim strategy memo; a filing checklist; an evidence log of dated conception and reduction-to-practice records; and a deadline calendar entry with reminders before the twelve-month conversion date. Filing is identity-bound: the system prepares a filing-ready package and posts an owner card stating what is asked, why it is gated, the default in effect (nothing is published), what the fleet prepared and a closing probe reading the filing receipt; it does not sign, pay or submit. For a principal who is not a patent professional the package is drafted from the repository record (design documents, code and dated history) rather than a questionnaire, with built and prophetic embodiments distinguished and questions for counsel listed; the output is a draft for professional review. Marketing function: segments, competition, positioning, a pitch kit, a promotion plan and a content calendar, each statement carrying a disclosure tag selected from SAFE NOW (an outcome-level statement that may be published while the gate probe has not held), AFTER FILING (names a mechanism and waits for the gate probe) and NDA ONLY (restricted to recipients under non-disclosure); the tags are data read by the public-text check. Funding: a funding map and a kit per program, submission being identity-bound. Events: a dated calendar tagged before or after the gate. Branding: a brand kit and profile contents. Legal and entity: comparison notes and owner cards marked for a professional; the system prepares and does not decide. Web presence: a site behind access control and noindex until the gate opens, with post-gate steps as backlog rows.

### 57.4 Generic-over-domain fallbacks and collaborative input

[0227] When the idea names a function without a stored definition, the planner replaces it by the generic function selected by a stored mapping: a tenant mapping, else a default pack of generic functions (research, plan, build, review, publish, fund, protect, report), else "research then plan then build then review" with a single-document schema and gate class `identity` if any step needs a signature, payment or account. The pack is parameterized by industry template (software, media, operations, research, nonprofit), and repository, tracker, runtime, publication target and executor are each interchangeable (sections 38 and 46).

[0228] "Collaborative input" means any message, edit, answer or file the principal supplies at any time without it being a precondition of progress; the planner runs on the idea file alone and the tick proceeds on every ready item. Each input is stored as a record and classified as a direction change (the planning step re-runs), an answer to an open question (applied as in section 49), a correction of an artifact (opening a work item and marking dependents stale) or a comment (stored). Every unanswered question has a default in effect; an owner card is created only for an irreversible, identity-bound step with no constructible reversible form; and the number of owner cards shown is capped (for example three, ranked by severity and nearness of deadline). Technical effect: the principal's attention is spent only on steps needing the principal's identity, and a period without input does not stop the chain.

### 57.7 Search and analytics integration in one platform

[0229] The web-presence function spans site, search and analytics in one data model. After the gate probe holds, domains are attached, noindex removed, site ownership verified and a sitemap submitted; a step needing the principal's account (granting a service account access) is an owner card closed by a probe observing the grant. Ingest workers read search and visit data for a complete past day into a signal store as rows `(date, source, channel, entity_type, entity_id, metric, value, quality)`; when a credential is missing or refused the worker writes a ledger row with the reason and no value, so the metric reads "not connected" and not zero. Loops act on the signals with a prediction recorded before acting: a page with impressions and a click-through below a threshold opens a title-and-description work item for the marketing persona; a query with impressions and no page opens a content item; a drop in sessions after a deploy opens an incident.

# ABSTRACT

A system operates an organization through a hierarchy of virtual staff agents, each defined by a persona record with a role, a program, metrics and an enumerated set of permitted operations. On ticks a portfolio-manager agent allocates focus capacity across programs by risk, and program-manager agents rank work and write priority records that an execution queue uses to dispatch work to executor processes; each operation is recorded with its prior value. Each decision carries a machine-readable prediction that is scored; a trust ledger per surface and action class maps verified outcomes to an autonomy ladder that selects each action's execution path. A plus loop reserves capacity for evidence-driven, additive changes to working products and keeps a change only when its outcome improves without guard regression. Only irreversible, identity-bound steps reach the human principal. Changes run under fenced claims, two-family review and probe-triggered revert; policy amends itself from recurring output signatures.
